# Nullus 설치 OSS CVE 대응 정책

Nullus 가 **설치해 주는** OSS(GitLab · Harbor · Argo CD · Keycloak …)에 CVE 가 공개됐을 때의 **탐지 → 판정 → 고지 → 패치 전달** 경로를 정한다. 도구 도입보다 운영 정책이 산출물이다.

- 작성: 2026-10-20 · 이슈: nullus-plan#78 (EPIC: 설치 OSS 스택 CVE 대응 정책)
- 상태: **적용 중** — 탐지 · 판정 · 고지와 "어느 검증된 업그레이드가 고치는가" 는 코드로 들어갔다(§8). 패치 전달은 #70(설치된 OSS 업그레이드)이 도구를 넓히는 만큼 넓어진다.
- 관련 문서
  - `docs/20_개발가이드/Nullus_릴리즈 정책.md` §7.4 — **Nullus 자체 이미지**(API · Web · Jenkins · SonarScanner)의 스캔 게이트와 "CVE 24시간 내 패치" 운영 정의. 이 문서와 짝이다
  - `docs/11_기능설계/Nullus_컨테이너_이미지_스캔_설계.md` §7(에어갭 DB 반입) · §12.4(설치 OSS 이미지 스캔)

## 0. 결정 요약

| 항목 | 결정 | 이유 |
|---|---|---|
| 추적 대상 | **Nullus 가 설치한 모든 이미지** + 스택이 쓰는 클러스터 공용 구성요소(cert-manager · metrics-server · External Secrets) | 스캔이 자동이라 대상을 넓혀도 비용이 없다. 대신 대응 기한을 노출 여부로 나눈다(§4) |
| 탐지 | 스택 Trivy 서버로 **설치 직후 1회 + 24시간마다 재스캔**. 에어갭은 내부 레지스트리 · 반입한 DB 로 같은 스캔 | 버전 카탈로그 대조는 "설정 · 백포트" 를 모른다. 이미지 스캔은 실제로 도는 바이너리를 본다 |
| 영향 판정 | 자동 1차 판정(수정판 · 심각도 · **외부 노출**) + 사람 2차 판정(설정 · 사용 여부 · 완화책) | "설치돼 있음 ≠ 취약함". 자동으로 가를 수 있는 것은 기계가, 나머지는 사람이 |
| 대응 기한 | **고지**와 **검증된 업그레이드 제공**을 나눈다. 외부 노출 CRITICAL: 24시간 내 고지 · 7일 내 검증 번들 | Nullus 는 상류 이미지를 빌드하지 않는다 — "24시간 내 패치" 를 그대로 약속할 수 없다 |
| 고지 채널 | 별도 채널 없이 **#63 알림 채널**에 `stack_cve_found` 이벤트. 에어갭은 사내 SMTP · 화면 · 릴리즈 노트 | 채널을 둘로 나누면 받는 사람이 둘을 관리해야 한다 |
| 에어갭 | 같은 스캔을 돌리되 **DB 기준일을 밝힌다**. 번들에 판정 결과(보안 공지)를 함께 싣는다 | 폐쇄망에서도 "무엇이 깔려 있고 무엇이 취약한가" 는 알아야 한다 |
| #70 과의 경계 | #78 = 탐지 · 판정 · 고지 · "어느 검증된 업그레이드가 고치는가". #70 = 업그레이드 실행 | 패치 전달 경로는 #70 이 소유한다 |

## 1. 범위 — 무엇을 추적하나

| 구분 | 대상 | 소관 |
|---|---|---|
| **이 문서** | 스택 네임스페이스에서 도는 모든 이미지 + 스택이 쓰는 공용 구성요소 | nullus-plan#78 |
| Nullus 자체 이미지 | `nullus-api` · `nullus-web` · `nullus-jenkins` · `nullus-sonar-scanner` | 릴리즈 정책 §7.4 (nullus-plan#77) |
| 사용자 앱 | 앱 이미지(파이프라인 게이트) · 앱 의존성(SCA) | 컨테이너 이미지 스캔 설계(#76) · 의존성 취약점 스캔 설계(#79) |

**14종 전체인가, 코어 N종인가** — 전체다. 스캔은 사람이 고르지 않고 실제로 도는 파드의 `imageID`(저장소@digest)를 모으므로, 템플릿에 도구가 늘어도 정책을 고칠 필요가 없다. 대상을 줄여서 얻는 것은 화면의 행 수뿐이고, 잃는 것은 "스캔하지 않은 곳" 이다.

**공용 구성요소** — cert-manager(`cert-manager`) · metrics-server(`kube-system`) · External Secrets(`external-secrets`)는 스택 네임스페이스 밖에 있지만 스택이 쓴다. 릴리스 라벨(`app.kubernetes.io/instance`)로 골라 함께 스캔하고 **공용**으로 표시한다. 설치기가 클러스터에 이미 있던 것을 재사용했어도 넣는다 — 스택이 그것에 기대기 때문이다. 다만 재사용한 것이 위 네임스페이스에 없거나 그 릴리스 라벨이 없으면(다른 네임스페이스의 cert-manager, 배포판 애드온 metrics-server 등) 찾지 못하고 건너뛴다 — 설치기는 CRD · APIService 로 재사용을 판단하지만 스캐너는 고정된 네임스페이스와 라벨로 찾는다. 패치 책임은 갈린다.

| 공용 구성요소를 누가 설치했나 | 패치 책임 |
|---|---|
| Nullus (설치 표시 `nullus.io/installed-by=nullus` 또는 옛 설치 지문) | Nullus — 이 문서의 기한을 따른다 |
| 클러스터에 원래 있던 것을 재사용 | 클러스터 관리자 — Nullus 는 고지만 한다 |

**스캐너가 없는 스택** — 이미지 스캐너(Trivy)를 고르지 않은 스택은 탐지 자체가 없다(`not_scanned` · `scanner_not_installed`, 화면이 "취약점 없음" 이 아니라고 밝힌다). 운영 스택은 Trivy 를 넣기를 권한다.

## 2. 탐지

| 항목 | 정의 |
|---|---|
| 방식 | 스택 Trivy 서버에 붙는 client Job(`nullus-image-scan`)이 스택이 돌리는 이미지를 digest 단위로 스캔한다 |
| 시점 | 설치 완료 직후 1회 + `STACK_IMAGE_RESCAN_INTERVAL`(기본 **24h**) 재스캔 — 설치 뒤 공개된 CVE 는 다시 스캔해야 보인다. API 가 다시 뜨면 마지막 스캔이 주기보다 오래된 스택부터 스캔한다(타이머가 재시작마다 처음부터 세어지므로) |
| 결과 | 이미지별 심각도 건수 · 수정판 있는 건수 · 취약점 목록 · **외부 노출** · **공용 여부** (`stack_image_scans`, `stack_image_vulnerabilities`) |
| 보는 곳 | 스택 상세 **이미지 취약점** 탭, `GET /api/v1/stacks/:id/image-scans` |
| 판정 | **보고만 한다.** 설치를 막지 않는다 — 상류 이미지의 CVE 는 사용자가 고칠 수 없는 경우가 많다 |

**왜 버전 카탈로그 대조가 아닌가** — "GitLab 17.7.0 은 CVE-X 에 취약" 같은 대조는 상류가 백포트한 패치, 배포판 패키지, 실제로 이미지에 든 바이너리를 모른다. 이미지 스캔은 그것을 직접 본다. 대조가 필요했던 유일한 이유는 에어갭이었는데, 에어갭에서도 스캔이 된다(아래).

**에어갭** — 노드는 containerd 미러로 이미지를 받아서 파드의 `imageID` 가 원래 레지스트리 이름(docker.io · quay.io …)이다. 스캔 Job 은 그것을 번들이 올린 내부 레지스트리 경로로 바꿔 받는다(`NULLUS_HELM_OCI_REGISTRY` 의 호스트 + 레지스트리 호스트를 뺀 경로 — `airgap/scripts/12-push-to-registry.sh` 의 규칙). 취약점 DB 는 번들이 반입한 것이다(컨테이너 이미지 스캔 설계 §7). 그래서:

- 결과에는 **DB 기준일**이 함께 보이고, 30일이 지나면 낡은 DB 로 표시된다
- 반입 뒤에 공개된 CVE 는 **다음 번들을 반입해야** 보인다 — 화면이 그렇게 밝힌다
- 반입 주기는 컨테이너 이미지 스캔 설계 §7.3 을 따른다

## 3. 영향 판정 — "설치돼 있음" ≠ "취약함"

### 3.1 자동 1차 판정

스캔 결과마다 세 가지를 기계가 가린다.

| 기준 | 어떻게 | 의미 |
|---|---|---|
| ① 수정판이 있는가 | Trivy 의 `FixedVersion` | 없으면 지금 할 수 있는 일이 없다 — 완화책만 |
| ② 심각도 | Trivy 심각도(CRITICAL · HIGH · …) | |
| ③ 외부 노출 | 스택 네임스페이스의 **HTTPRoute → Service selector → 파드** 를 따라가 게이트웨이로 클러스터 밖에 열린 이미지를 가린다(호스트 이름 포함). **LoadBalancer · NodePort Service** 가 고르는 파드도 노출이다 — 스택 게이트웨이의 Envoy 데이터플레인이 그렇게 밖의 요청을 직접 받으므로 스택의 모든 라우트 호스트로 노출된 것으로 본다 | 밖에서 닿는 서비스의 것을 먼저 고친다 |

세 가지로 등급을 매긴다.

| 등급 | 조건 |
|---|---|
| **A** | CRITICAL · 수정판 있음 · **외부 노출** |
| **B** | CRITICAL · 수정판 있음 · 내부 |
| **C** | HIGH · 수정판 있음 |
| **D** | 수정판 없음(심각도 무관) |

외부 노출은 HTTPRoute 와 LoadBalancer · NodePort Service 로 본다. Ingress 는 보지 않는다 — 스택이 만드는 브리지 Ingress 는 Envoy 를 가리킬 뿐이라 Envoy 가 노출로 잡히지만, 손으로 더한 Ingress 가 ClusterIP Service 를 가리키면 기계는 모른다(2차 판정에서 본다). Gateway API CRD 가 없는 클러스터에서는 라우트로 열린 것만 모른다.

### 3.2 사람 2차 판정

A · B 는 사람이 한 번 더 본다. 판정 주체는 **Nullus 릴리즈 담당**(릴리즈 정책 §9.3)이고, 고객 쪽에서는 **스택 운영자**다.

- 그 패키지가 실제로 쓰이는가 — 같은 이미지라도 취약한 기능을 켜지 않았을 수 있다(예: GitLab 의 특정 통합)
- 알려진 익스플로잇이 있는가(CISA KEV 등) — 있으면 A 로 올린다
- 완화책 — 기능 끄기 · 네트워크 정책 · 게이트웨이에서 경로 막기

판정 결과(영향 없음 · 완화 · 업그레이드 필요)는 Nullus 릴리즈 노트 `### Security` 에 남긴다(§5.2).

## 4. 대응 기한

Nullus 는 설치 OSS 의 상류 이미지를 빌드하지 않는다. 그래서 자체 이미지의 "CVE 24시간 내 패치 릴리즈"(릴리즈 정책 §7.4)를 그대로 약속할 수 없다 — 상류가 수정판을 내야 하고, 그것을 실클러스터에서 리허설해 검증된 업그레이드로 올려야 한다. 약속을 **고지**와 **검증된 업그레이드 제공** 둘로 나눈다.

| 등급 | 고지 | 검증된 업그레이드 제공 |
|---|---|---|
| **A** (CRITICAL · 수정판 · 외부 노출) | **24시간 내** — 재스캔 주기(24h)가 곧 자동 고지 시점이다(심각도 `critical`) | **7일 내** 업그레이드 번들 `verified` 등록, 또는 완화책 공지 |
| **B** (CRITICAL · 수정판 · 내부) | 24시간 내 자동 고지(심각도 `warning`) | **30일 내** 또는 다음 정기 릴리즈 중 빠른 쪽 |
| **C** (HIGH · 수정판) | 화면 · 정기 점검 | 분기 OSS 버전 갱신(템플릿 기본 버전) |
| **D** (수정판 없음) | 화면. A·B 급이면 완화책 공지 | 수정판이 나온 시각부터 위 기한 |

- **기한의 기준 시각** — 그 CVE 를 처음 고지한 시각(`stack_cve_found` 를 보낸 스캔, `stack_cve_notices.first_notified_at`)
- **못 지킬 때** — 릴리즈 노트 `### Security` 에 사유와 다음 목표일을 적는다. 목표일은 다음 정기 릴리즈를 넘기지 않는다
- **업그레이드 경로가 아직 없는 도구** — 지금 검증된 업그레이드는 Argo CD 만 있다(#70). 다른 도구는 (1) 템플릿 기본 버전을 올린 Nullus 릴리즈(새 설치) (2) 검증된 절차 문서로 수동 업그레이드를 안내한다. #70 이 도구를 넓히는 만큼 (2)가 줄어든다

> **PRD · 기능목록의 "CVE 24시간 내 패치"** 는 Nullus 자체 이미지의 약속이다(릴리즈 정책 §7.4). 설치 OSS 는 이 문서의 표를 따른다 — 둘을 같은 문장으로 묶지 않는다.

## 5. 고지

### 5.1 자동 고지 — `stack_cve_found`

별도 공지 채널을 두지 않고 #63 의 조직 알림 채널(Telegram · 이메일 · Slack)에 이벤트 하나를 얹는다.

| 항목 | 정의 |
|---|---|
| 언제 | 재스캔이 아직 알리지 않은 **수정판 있는 CRITICAL**(A · B)을 찾았을 때. "알렸는가" 는 스캔 결과가 아니라 알린 기록(`stack_cve_notices`)으로 가린다 |
| 묶음 | 스택당 한 건. 본문에 CVE 다섯 개까지(패키지 설치→수정 버전 · 이미지 셋까지 · 노출 호스트), 나머지는 수만 |
| 심각도 | A 가 하나라도 있으면 `critical`, 아니면 `warning` |
| 첫 고지 | 스택에 처음 보내는 것은 지금 있는 것을 "첫 고지" 로 한 번에 알린다 — 새 스택이면 설치 시점의 것, 이 기능 전에 설치한 스택이면 지금의 현황 |
| 중복 | 보내기 전에 알린 기록을 선점한다(기본 키, `INSERT … RETURNING`). API 레플리카 둘이 같은 시각에 재스캔해도 한 번만 간다 |
| 보내지 않는 것 | HIGH · 수정판 없음(화면으로 본다), **이미 알린 것**(이미지 스캔이 한 번 실패해 취약점 행이 사라졌다 돌아와도), 알린 기록을 읽거나 남기지 못한 경우(이번엔 건너뛰고 다음 스캔이 다시 본다) |
| 구독 | 새 채널은 기본으로 켜진다. 이 이벤트 전에 만든 채널은 편집해 체크해야 받는다 |
| 실패 | 보내지 못해도 스캔은 성공이다. 발송 기록(최근 발송)에 실패가 남고, 그 CVE 를 다시 보내지는 않는다 — 다시 보내면 받은 채널에 같은 알림이 반복해 간다. 종료로 취소돼 못 보낸 것만 다음 스캔이 보낸다 |

같은 CVE 를 매 스캔마다 보내지 않는다 — 매일 같은 알림이 오면 아무도 읽지 않는다.

### 5.2 Nullus 측 고지

릴리즈 담당은 A · B 판정과 대응(업그레이드 번들 · 완화책 · 영향 없음)을 릴리즈 노트(CHANGELOG `### Security`)에 적는다. 이것이 고객이 "Nullus 는 이 CVE 를 어떻게 보는가" 를 묻는 곳이다.

### 5.3 에어갭 고객

- 외부로 나가지 못하므로 알림 채널은 **사내 SMTP 릴레이**가 현실적이다(이메일 채널)
- 스캔은 반입한 DB 기준이다 — 반입 뒤의 CVE 는 다음 반입 때 들어온다
- 에어갭 번들의 릴리즈 노트(`### Security`)가 §5.2 의 판정을 함께 싣는다 — 폐쇄망 고객은 DB 를 기다리지 않고 Nullus 의 판정을 받는다

## 6. 패치 전달 — #70 과의 경계

| | #78 (이 문서) | #70 설치된 OSS 업그레이드 |
|---|---|---|
| 하는 일 | 탐지 · 판정 · 고지 · "어느 검증된 업그레이드가 이 CVE 를 고치는가" | 검증된 업그레이드 번들의 사전 점검 · 적용 · 되돌리기 |
| 산출물 | 스캔 결과, `stack_cve_found`, 릴리즈 노트 Security | `upgrade_bundles`(verified), 업그레이드 실행 기록(`stack_upgrade_runs`) |
| 이음매 | 업그레이드 번들의 **고치는 CVE 목록**(`fixes_cves`, 000105)을 읽는다. 업그레이드 후보가 그중 **이 스택의 그 릴리스 이미지에서 지금 발견된 것**(`fixes_found`)을 계산하고, 버전 업그레이드 탭이 "이 스택에서 발견된 CVE N건을 고칩니다" 와 그 목록을 보인다 | 번들을 리허설해 `verified` 로 올릴 때 고치는 CVE 를 함께 적는다 |

`fixes_found` 는 스택의 설치 이미지 스캔 결과를 릴리스 이름으로 모아 대조한다. 공용 구성요소는 스택 업그레이드 대상이 아니므로 뺀다. 스캔 결과를 읽지 못해도 후보 목록은 막지 않는다 — 고치는 CVE 를 보이지 못할 뿐이다.

업그레이드는 임의 버전으로 올리지 않는다 — 실클러스터 리허설로 `verified` 가 된 번들만 실행한다(OSS 업그레이드 설계). 그래서 "CVE 를 고치는 상류 버전이 나왔다" 와 "고객이 올릴 수 있다" 사이에 리허설이 있고, 그 기간이 §4 의 "검증된 업그레이드 제공" 기한이다.

## 9. 남은 과제

- **업그레이드 지원 도구 확대** — 지금은 Argo CD 만 검증된 업그레이드가 있다(#70). 그 밖의 도구는 §4 의 "수동 안내" 경로다
- **취약점 쪽에서 업그레이드로 잇기** — 지금은 버전 업그레이드 탭이 "이 업그레이드가 고치는 CVE" 를 보인다. 이미지 취약점 탭의 CVE 행에서 그것을 고치는 검증된 업그레이드로 가는 길은 아직 없다
- **익스플로잇 정보 자동 반영** — CISA KEV · EPSS 를 1차 판정에 넣으면 사람 판정이 준다. 에어갭에서 같은 정보를 어떻게 반입할지가 먼저다
- **노출 판정 범위** — 손으로 더한 Ingress(ClusterIP Service 를 가리키는 것)는 보지 않는다
- **재사용한 공용 구성요소 찾기** — 스캐너는 고정 네임스페이스 · 릴리스 라벨로 찾는다. 설치기가 판단한 위치(CRD 주석 · APIService)를 넘겨받으면 다른 네임스페이스의 cert-manager 나 애드온 metrics-server 도 스캔할 수 있다
- **릴리스 이름의 출처** — 스캔 결과의 릴리스는 파드 라벨(`app.kubernetes.io/instance` 등)에서 읽는다. 오퍼레이터가 만드는 파드(Prometheus · Alertmanager 는 CR 이름, Envoy 는 라벨 없음)는 Helm 릴리스 이름과 다르다. 지금 검증된 업그레이드는 Argo CD 뿐이라 맞지만, 도구가 늘면 `fixes_found` 가 조용히 빌 수 있다
- **스캔 Job 이름 충돌** — 레플리카 둘이 같은 스택을 동시에 스캔하면 같은 이름의 Job(`nullus-image-scan`)을 서로 지워 그 회차 결과가 실패할 수 있다(고지는 선점으로 한 번만 간다). 스택 단위 잠금이 필요하다
- **기존 채널의 이벤트 구독** — 이 이벤트 전에 만든 채널은 자동으로 받지 않는다(받지 않은 것을 기본으로 켜면 고객 채널에 예고 없이 새 알림이 간다)
- **Security Dashboard(#65)** — 조직의 모든 스택의 설치 OSS CVE 현황을 한 화면에 모은다
