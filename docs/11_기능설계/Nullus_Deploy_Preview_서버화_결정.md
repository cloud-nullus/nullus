# Deploy Preview 서버화 여부 결정 (nullus-plan#34)

> EPIC: [cloud-nullus/nullus-plan#34](https://github.com/cloud-nullus/nullus-plan/issues/34) — Deploy Preview 서버화 여부 결정.
> 본 문서는 결정 카드다 — 산출물은 이 문서뿐이고, 구현은 별도 작업으로 분리한다.

작성일: 2026-08-15

---

## 요약 (비관계자용 — 이것만 읽어도 논의 가능)

**무엇이 문제인가.**
Nullus 설치 마법사에는 "이런 설정으로 설치됩니다"를 미리 보여주는 미리보기 화면이 있다. 그런데 이 미리보기는 **브라우저(프론트엔드)가 자체 계산해서 그린 것**이고, 실제 설치는 **서버가 따로 계산한 값**으로 진행된다. 같은 결과를 두 곳에서 각자 만들다 보니, 미리보기에 보인 내용과 실제로 설치되는 내용이 **어긋날 수 있는 구조**다. 실제로 과거에 "화면에 보이는 도구 버전 11개 중 9개가 실제 설치 버전과 달랐던" 사고가 있었고, 원인이 같은 구조(화면 따로·서버 따로)였다.

**왜 브라우저 쪽을 고치는 것으로는 해결이 안 되는가.**
설치에 들어가는 값 중 일부(예: 자동 생성되는 비밀번호와 그 연결 정보)는 **설치하는 순간 서버가 만들어내는 값**이라, 설치 전 브라우저가 아무리 잘 계산해도 미리 알 방법 자체가 없다. 즉 브라우저 미리보기는 노력 부족이 아니라 **원리적으로 정확해질 수 없다**.

**무엇을 결정했는가.**
서버가 미리보기를 만들어 주는 것이 필요하다(= "서버화가 필요하다"는 결론). 단, 한 번에 다 만들지 않고 두 단계로 나눈다:

1. **1차 — "실제 설치값 미리보기"**: 사용자가 마법사에서 고른 내용을 서버에 보내면, 서버가 **실제 설치 때 쓰는 것과 동일한 계산 코드**로 설치 설정값을 조립해 돌려준다. 미리보기와 실제 설치가 같은 코드를 쓰므로 어긋날 방법이 없어진다. 클러스터 접속이나 무거운 작업이 필요 없어 가볍고 빠르다.
2. **2차(선택 기능) — "설치 리허설"**: 원하는 사용자가 버튼을 누르면, 서버가 대상 클러스터를 상대로 **실제 설치 직전까지의 전 과정을 리허설**(dry-run: 반영 없이 결과만 계산)해서 최종 결과물까지 검증해 준다. 몇 초의 대기가 있어 기본 동작이 아니라 선택 기능으로 둔다.

**참고할 선례.**
이미 배포가 끝난 스택의 설정을 고치는 화면(Config 탭)은 과거에 같은 문제를 겪고 **서버 리허설 방식으로 전환**해 해결했다. 이번 결정은 그 검증된 방식을 설치 마법사에도 확장하는 것이다.

**이 결정으로 당장 무엇이 바뀌나.**
아무 코드도 바뀌지 않는다. 이 문서는 "필요한가?"라는 질문에 대한 결론이며, 실제 구현은 별도 이슈로 분리해 우선순위를 다시 판단한다.

## 상세 (근거와 코드 위치)

### 1. 현재 상태 — 미리보기 경로는 이미 둘로 갈라져 있다

| 경로 | 미리보기를 만드는 곳 | 정확도 |
|---|---|---|
| **설치 마법사** (`/stack/install`) | **브라우저가 자체 생성** — `web/src/features/stack/utils/install-manifest-builders.ts` **902줄**이 차트 정보·설치 방식·TLS 정책·설정값을 프론트에서 따로 구현 | ⚠️ §2 참조 |
| **배포 후 설정 편집** (Config 탭) | **서버가 리허설로 생성** — `POST /stacks/:stackId/releases/:releaseName/values/preview`가 helm 업그레이드를 dry-run(반영 없는 리허설)으로 돌려 실제 적용될 값을 돌려준다 (`internal/stack/adapter/helm/release-values.go:229-236`) | ✅ 실제 렌더 검증 |

설치 경로에 있는 다른 API들은 미리보기가 아니다 — `POST /stacks/:id/validate`는 도구 호환성 검증, `POST /stacks/estimate`는 리소스 사용량 추정만 한다. **설치 경로에는 서버가 보증하는 미리보기가 없다.**

이 갈라짐은 팀이 이미 한 번 기록했다 — CHANGELOG(스택 설정 수정 기능, F040): *"Monaco 에디터는 설치 마법사에만 있었고, 거기 뜨는 YAML 도 프론트가 만든 매니페스트라 백엔드가 실제로 helm 에 넘긴 values 와 달랐다."* 편집 경로는 그때 서버 리허설로 고쳤고, **설치 경로는 그대로 남아 있다.**

### 2. 핵심 관찰 — 미리보기는 두 층이고, 한 층만 거짓말을 한다

설치 마법사 미리보기를 뭉뚱그려 "부정확하다"고 하면 틀린다. 층을 갈라야 한다.

**(1) 사용자가 직접 입력한 층 — 정확하다.**
마법사의 편집기에서 사용자가 고친 YAML은 `yaml_overrides`라는 이름으로 **그대로 서버에 전송·저장**된다 (`stack-install-page.tsx:1002` → `internal/stack/domain/config.go:10`의 `StackConfig.YAMLOverrides`). 화면에 보이는 것이 곧 서버로 가는 입력이므로, 이 층의 미리보기는 정의상 진실이다.

**(2) 플랫폼이 계산해 넣는 층 — 구조적으로 허구다.**
서버는 설치할 때 `internal/stack/adapter/helm/values.go`에서 설정값을 독자적으로 조립하는데, 브라우저는 그 내용을 알 수 없고, 일부는 알 방법 자체가 없다:

- **자동 생성 비밀번호의 배선**: 비밀번호는 설정값에 직접 넣지 않는다 — 설치 시점에 생성되어 시크릿 저장소(OpenBao)에 기록되고, 복제된 Secret을 `existingSecret`으로 참조한다(`values.go:90-99`). **설치 전에는 존재하지 않는 값이라 브라우저 미리보기가 원리적으로 재현할 수 없다.**
- **접속 주소 재계산**: 서비스 외부 주소(externalURL)는 서버가 접속 도메인 설정으로 다시 채운다(`values.go:152-154`).
- **차트 정보의 이중 소유**: 브라우저 코드가 차트 저장소·이름 목록(`TOOL_HELM_META`)을 서버와 별도로 들고 있고, 모르는 도구는 `https://charts.example.com`이라는 **가짜 주소로 지어낸다**(`install-manifest-builders.ts:92`).
- **같은 구조가 실제 사고를 낸 전례**: 화면의 도구 버전 표가 서버 상수와 **11개 중 9개** 어긋나 있었다(CHANGELOG Fixed 항목). 테스트로 가드를 추가했지만, "같은 정보를 두 곳이 각자 소유한다"는 구조 자체는 남아 있다.

### 3. 실패 유형 정리 — 미리보기 ≠ 실제 설치 입력이 되는 경우

| # | 유형 | 원인 | 브라우저 쪽에서 해소 가능? |
|---|---|---|---|
| 1 | 자동 생성 비밀번호 배선 누락/오표시 | 설치 시점 생성 + OpenBao/ESO 참조 | **불가능** (원리적) |
| 2 | 접속 주소(externalURL) 재계산 차이 | 서버가 다시 채움 | 재구현하면 가능하나 어긋남 재발 |
| 3 | 차트 저장소/이름 어긋남 | 브라우저·서버 이중 소유, 가짜 기본값 | 상동 |
| 4 | 도구 버전 어긋남 | 이중 소유 (실사고 전례 9/11) | 테스트 가드뿐, 구조 미해결 |
| 5 | 설치 방식(helm/yaml)·TLS 정책 차이 | 브라우저 자체 판정 | 상동 |
| 6 | 사용자가 직접 고친 값 | — | **이미 정확** (입력 그 자체) |

유형 1 하나만으로 결론이 난다: **브라우저 미리보기를 아무리 고쳐도 서버가 보증하는 진실이 될 수 없다.** 이중 구현을 계속 동기화해야 하는 유지비(유형 2~5)는 덤이다.

### 4. 검토한 선택지와 결정

| 선택지 | 내용 | 판정 |
|---|---|---|
| **현상 유지** | 브라우저 미리보기를 그대로 둔다 | ❌ §2~3 — 구조적 허구 + 이중 유지비 |
| **실제 설치값 미리보기** (서버가 설정값 조립) | 마법사 입력을 서버로 보내면, 실제 설치와 **동일한 코드**(`values.go`)로 설정값을 조립해 돌려준다. 클러스터 접속·차트 다운로드 불요 | ✅ **1차 채택** |
| **설치 리허설** (클러스터 대상 dry-run) | 선택된 클러스터에 `helm install --dry-run`으로 최종 결과물(매니페스트)까지 리허설 | ⚪ **2차, 선택 기능으로** (버튼식) |
| **미리보기 축소·정직화** | 플랫폼 계산 층을 "근사치"로 표기하거나 숨긴다 | ⚪ 1차 도입 전의 임시 조치로만 |

**결정: "실제 설치값 미리보기"를 1차로, "설치 리허설"을 2차 선택 기능으로 도입한다.**

- **1차를 먼저 하는 이유**: 실패 유형 1~4가 한 번에 사라진다 — 미리보기와 실제 설치가 **같은 코드를 쓰므로 어긋날 방법이 없다.** 클러스터·차트 다운로드가 없어 가볍고, 편집 경로의 preview API와 대칭이라 API 모양도 이미 검증된 셈이다. 902줄짜리 브라우저 빌더는 "미리보기 진실의 출처" 역할을 내려놓고 단계적으로 줄일 수 있다.
- **리허설을 일괄 도입하지 않는 이유**: 마법사는 등록·검증된 클러스터를 먼저 고르므로 클러스터 도달성은 문제가 아니다. 문제는 비용 대비 증분 — 1차가 설정값 수준의 진실을 확보한 뒤, 리허설이 추가로 주는 것은 차트 렌더(최종 매니페스트) 검증뿐이다. 몇 초의 대기를 감수하고라도 보고 싶은 사용자를 위한 명시적 버튼이 알맞다. 구현 시에는 편집 경로가 이미 밟은 Helm SDK 함정 3종의 해법을 그대로 쓴다 — 마지막 정상 배포본 읽기, 서브차트 유실 시 동일 버전 재취득, bitnami 차트의 `lookup` 대응 서버측 dry-run 옵션(CHANGELOG F040).

### 5. 범위 주의

- 본 카드의 산출물은 **이 결정 문서뿐**이다. 1차/2차 구현은 별도 이슈로 분리한다. 대상은 스택 모듈(기능 현황상 "구현됨"인 F4 영역)이라, 아직 안정화 중인 CI/CD 영역(F5/F6)과는 무관하다.
- 1차를 도입해도 비밀번호 등 시크릿 값 자체는 미리보기에 노출하지 않는다 — 실제 설치처럼 Secret **참조 이름**만 보인다(감사 로그가 값 대신 키만 남기는 것과 같은 원칙).
