로컬 E2E · macOS

Nullus를 로컬에서 처음부터 끝까지

처음 설치하고 띄운 뒤 GitLab + Argo CD + SonarQube 스택을 깔고, CI/CD 파이프라인을 돌리고, 백업 → 삭제 → 복구를 거쳐 그 파이프라인을 이어서 돌리는 한 바퀴다. 각 단계는 실제 스크립트와 코드에서 확인한 명령만 적었다.

기준 main 040c480 + 설치 화면·파이프라인 SAST 변경 · 2026-10-10 소요 반나절 (스택 설치만 40분~2시간) 대상 처음 로컬 환경을 꾸리는 개발자

SonarQube는 설치부터 파이프라인 분석까지 된다템플릿 gitlab-argocd-sonarqube-v1(또는 설치 화면 Security 탭의 SonarQube)이 SonarQube를 스택에 함께 깔고, 관리자 비밀번호를 바꾸고, Keycloak(SAML) 로그인을 붙인다. 그 스택의 파이프라인에는 sast 단계가 생겨 Quality Gate 를 통과해야 배포된다(스택 정책으로 경고로 바꿀 수 있다 — 부록 B).
삭제는 "네임스페이스 삭제"로 한다백업·복구가 리허설된 경로가 이것뿐이다. 화면의 스택 삭제나 stack-down 뒤 복구는 아직 되지 않는다(11단계).
배지 읽는 법실측 기록은 CHANGELOG·리허설에 실제로 돌린 기록이 있는 단계, 코드 기준은 코드를 읽고 쓴 단계다. 후자는 처음 돌리는 사람이 확인하게 된다.
몇 군데는 손이 간다GitLab 포트포워딩, 백업 설정, 복구 후 주소 갱신은 아직 자동화되지 않았다. 해당 단계에 수동 표시가 있다.

준비

01

준비물

실측 기록

도구는 Homebrew로 한 번에 깐다. Docker는 Docker Desktop이나 OrbStack 중 하나를 쓴다.

터미널
brew install go node kind kubectl helm jq libpq
brew install --cask orbstack      # 또는 Docker Desktop
도구버전비고
Go1.26.1 이상README의 "1.24+"는 낡았다. go.mod가 1.26.1을 요구한다
Node22.12 이상Vite 8 요구사항
helm3.x 또는 4.xREADME 기준은 3.x. preflight는 "선택"이라 표시하지만 up은 없으면 멈춘다
kind · kubectl최신로컬 클러스터 2개를 만든다
jq · python3—스크립트가 쓴다. python3는 macOS 기본
libpqPostgres 17 이상백업이 pg_dump를 부른다(10단계)
Docker에 자원을 넉넉히 준다GitLab 스택은 무겁다. 템플릿 계획값이 12 vCPU · 24 GiB(SonarQube 포함)이고, 4 vCPU 환경에서는 GitLab 스택이 뜨지 않았다는 기록이 있다. SonarQube는 분석 없이 떠 있기만 해도 메모리를 2.7 GiB 쓴다. Docker 설정에서 CPU 8개 이상, 메모리 20 GB 이상(가능하면 24 GB)을 준다.

저장소를 받는다.

터미널
git clone https://github.com/cloud-nullus/nullus.git
cd nullus
PATH 확인go·kubectl·helm이 "command not found"면 export PATH=/opt/homebrew/bin:$PATH를 셸 설정에 넣는다. API는 로그인 셸(bash -l)로 뜨므로 ~/.bash_profile이나 ~/.zprofile에서도 보여야 한다.

실측 기록

up --kind 하나가 Postgres·Redis·MinIO·Keycloak을 띄우고, 마이그레이션을 돌리고, API(8090)와 웹(5173)을 띄우고, kind 클러스터 둘을 만들어 Nullus에 등록한다.

터미널
./scripts/runbook_local.sh preflight
./scripts/runbook_local.sh up --kind
./scripts/runbook_local.sh status
./scripts/runbook_local.sh smoke
서비스주소계정
웹http://localhost:51733단계 참고
APIhttp://localhost:8090개발 모드라 인증 없음
Postgreslocalhost:5433nullus / nullus_dev
MinIOlocalhost:9000 (콘솔 9001)nullus / nullus_dev
Keycloakhttp://localhost:8180admin / admin

all 대신 up을 쓴다runbook_local.sh all은 도중에 실패하면 띄운 것을 전부 내린다. 처음에는 up과 smoke를 따로 돌려야 어디서 막혔는지 남는다.

확인

  • status에서 API /health가 OK이고 kind 노드가 Ready다
  • smoke가 실패 없이 끝난다
  • 로그는 ./scripts/runbook_local.sh logs api로 본다
03

로그인·클러스터 확인

실측 기록

http://localhost:5173을 열면 Keycloak 로그인으로 넘어간다. admin@nullus.io / nullus123!로 들어간다.

Keycloak 없이 가볍게 보려면up --kind --auth=none으로 띄우면 모의 로그인 화면이 나온다(admin@nullus.dev / admin123). 이때 이후의 refresh에도 똑같이 --auth=none을 붙여야 한다.

이제부터 쓸 터미널 변수를 정해 둔다. 새 터미널을 열 때마다 다시 넣으므로 파일로 둔다.

~/.nullus-e2e.env 만들기
cat > ~/.nullus-e2e.env <<'EOF'
export API=http://localhost:8090
export CTX=kind-nullus-platform
export NS=nullus-gitlab-argocd-sonarqube # 스택 이름이자 네임스페이스 (stack-up 기본값)
export DOMAIN=nullus.local
export ORG=11111111-1111-1111-1111-111111111111
export APP=demo-api                     # 8단계에서 만들 앱
export APP_NS=demo                      # 앱이 배포될 네임스페이스
EOF
source ~/.nullus-e2e.env

클러스터 두 개가 등록됐는지 본다.

터미널
curl -s $API/api/v1/admin/clusters | jq '.items[] | {name, types}'

확인

  • kind-nullus-platform(pipeline)과 kind-nullus-develop(target)이 보인다
  • 안 보이면 API가 떠 있는 상태에서 ./scripts/register-kind-clusters.sh를 돌린다

스택

04

GitLab + Argo CD + SonarQube 스택 설치

실측 기록 (GitLab + Argo CD)실측 기록 (SonarQube 단계)코드 기준 (템플릿 전체)

템플릿 gitlab-argocd-sonarqube-v1은 GitLab CE · GitLab Runner · GitLab Registry · MinIO · Argo CD · Prometheus · Grafana에 SonarQube Community를 더해 깐다. SonarQube는 스택의 PostgreSQL 안에 전용 DB(sonarqube)를 만들어 쓴다. CLI로 깔아야 설치가 끝난 뒤 kind 노드에 레지스트리 주소와 내부 CA까지 넣어 준다. 화면으로 깔면 이 배선이 빠진다.

터미널
./scripts/runbook_local.sh stack-up --template=gitlab-argocd-sonarqube-v1 --wait
STACK_ID=$(curl -s $API/api/v1/stacks | jq -r --arg n "$NS" '.items[] | select(.name==$n) | .id' | head -1)
echo "export STACK_ID=$STACK_ID" >> ~/.nullus-e2e.env      # 출력의 "stack created: stk_..." 와 같아야 한다

기본값은 이름·네임스페이스 nullus-gitlab-argocd-sonarqube, 도메인 nullus.local, 클러스터 kind-nullus-platform이다. 다른 터미널에서 파드가 뜨는 것을 본다.

다른 터미널
source ~/.nullus-e2e.env
kubectl --context $CTX -n $NS get pods -w
60분에서 기다림이 끊기면--wait는 60분까지만 기다린다. 끊겼으면 ./scripts/runbook_local.sh stack-status $STACK_ID --wait로 이어서 기다리고, 완료 뒤 부록 A의 "노드 배선" 명령을 직접 돌린다. 끊기면 노드 배선이 실행되지 않기 때문이다.
SonarQube 없이 가볍게 하려면--template=gitlab-argocd-v1로 깔고 환경 파일의 NS를 nullus-gitlab-argocd로 바꾼다. 5단계의 SonarQube 줄과 부록 B는 건너뛴다.

확인

  • 마지막에 kind 노드 배선 완료가 찍힌다
  • sonarqube-0이 1/1 Running이고 nullus-sonarqube-bootstrap Job이 Complete다(SonarQube가 처음 뜨는 데 2분쯤 걸린다)
  • curl -s $API/api/v1/stacks/$STACK_ID | jq .state 가 "completed"다
  • 파드가 실제로 떠 있다: kubectl --context $CTX -n $NS get pods --no-headers | wc -l이 0이 아니다(0이면 시뮬레이션으로 "완료"된 것이다)
05

도구 열기

실측 기록

스택 도구는 게이트웨이 뒤에서 gitlab.nullus.local, argocd.nullus.local, sonarqube.nullus.local 같은 이름으로 갈린다. kind에는 외부 로드밸런서가 없으므로 스크립트가 도커 네트워크 안에 443 라우터를 세운다. sudo가 필요 없다.

터미널
./scripts/port-forward-gateway.sh
./scripts/port-forward-gateway.sh --hosts          # /etc/hosts 에 넣을 줄을 보여 준다
./scripts/port-forward-gateway.sh --hosts | sudo tee -a /etc/hosts

./scripts/setup-local-domain.sh                    # 내부 CA 를 꺼내고 신뢰 등록 명령을 알려 준다
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain .runbook-logs/nullus-internal-ca.crt

초기 비밀번호는 클러스터의 Secret에서 꺼낸다.

터미널
# GitLab — 사용자 root
kubectl --context $CTX -n $NS get secret gitlab-initial-root-password \
  -o jsonpath='{.data.password}' | base64 -d; echo
# Argo CD — 사용자 admin
kubectl --context $CTX -n $NS get secret argocd-initial-admin-secret \
  -o jsonpath='{.data.password}' | base64 -d; echo
# SonarQube — 관리자 admin. 일반 사용자는 로그인 화면의 Keycloak 버튼으로 들어간다
kubectl --context $CTX -n $NS get secret nullus-sonarqube-credentials \
  -o jsonpath='{.data.admin-password}' | base64 -d; echo
연결 정보 창과 Secret 이름이 다를 수 있다화면의 연결 정보는 gitlab-gitlab-initial-root-password를 가리키지만, 설치기는 GitLab 비밀번호를 gitlab-initial-root-password로 만든다. 앞의 것이 없으면 위 명령을 쓴다.

확인

  • https://gitlab.nullus.local에 root로 로그인된다
  • https://argocd.nullus.local에 admin으로 로그인된다
  • https://sonarqube.nullus.local에 admin으로 로그인되고, admin / admin은 거부된다
  • SonarQube 로그인 화면의 Keycloak 버튼으로 admin@nullus.io가 들어가진다(일반 사용자 권한). --auth=none으로 띄웠으면 버튼이 없다 실측 기록 (SAML 흐름)
06

API 연결 설정 — GitLab 주소와 백업

실측 기록수동

로컬 API는 클러스터 밖(맥)에서 돈다. 그래서 두 가지를 손으로 넣어야 한다.

  • GitLab 주소: 파이프라인을 만들 때 API가 GitLab에 저장소를 만든다. 기본 주소는 클러스터 내부 DNS라 맥에서 풀리지 않는다.
  • 백업 설정: 백업 모듈은 암호화 키와 목적지가 없으면 꺼진 채로 뜬다. 나중에 따로 재기동하지 않도록 지금 함께 넣는다.

① GitLab 포트포워딩. 끊기면 다시 잇도록 반복문으로 띄운다. 이 터미널(또는 백그라운드)은 끝까지 살려 둔다.

터미널
( while true; do
    kubectl --context $CTX -n $NS port-forward svc/gitlab-webservice-default 8181:8181 >/dev/null 2>&1
    sleep 2
  done ) &
echo $! > /tmp/nullus-gitlab-pf.pid

② 백업 목적지 준비. 로컬 MinIO(localhost:9000)를 목적지로 쓴다. 스택 안의 MinIO는 스택과 함께 지워지므로 쓰면 안 된다. 로컬 Keycloak은 Postgres DB가 없으므로 빈 DB를 대역으로 만든다.

터미널
docker compose -f docker-compose.dev.yaml exec minio \
  mc alias set local http://localhost:9000 nullus nullus_dev
docker compose -f docker-compose.dev.yaml exec minio mc mb local/nullus-backup
docker compose -f docker-compose.dev.yaml exec postgres \
  psql -U nullus -d nullus -c 'CREATE DATABASE keycloak;'

③ API 환경 파일을 만들고 재기동한다.

~/.nullus-api.env 만들기 + 재기동
cat > ~/.nullus-api.env <<'EOF'
NULLUS_GITLAB_URL=http://127.0.0.1:8181
NULLUS_BACKUP_ENABLED=true
# 정확히 32바이트, ENCRYPTION_KEY·DB 비밀번호와 다른 값
NULLUS_BACKUP_SEAL_KEY='nullus-backup-seal-key-32bytes!!'
NULLUS_BACKUP_DESTINATION_ENDPOINT=localhost:9000
NULLUS_BACKUP_DESTINATION_BUCKET=nullus-backup
NULLUS_BACKUP_DESTINATION_ACCESS_KEY=nullus
NULLUS_BACKUP_DESTINATION_SECRET_KEY=nullus_dev
NULLUS_BACKUP_DESTINATION_USE_SSL=false
NULLUS_BACKUP_KEYCLOAK_DATABASE_HOST=localhost
NULLUS_BACKUP_KEYCLOAK_DATABASE_PORT=5433
NULLUS_BACKUP_KEYCLOAK_DATABASE_NAME=keycloak
NULLUS_BACKUP_KEYCLOAK_DATABASE_USER=nullus
NULLUS_BACKUP_KEYCLOAK_DATABASE_PASSWORD=nullus_dev
EOF

set -a; source ~/.nullus-api.env; set +a
export PATH="$(brew --prefix libpq)/bin:$PATH"     # pg_dump
./scripts/runbook_local.sh refresh                 # up 을 --auth=none 으로 띄웠으면 여기도 붙인다
grep '백업 모듈 준비 완료' .runbook-logs/api.log
재기동할 때마다 이 파일을 먼저 읽힌다refresh를 다시 돌릴 때 set -a; source ~/.nullus-api.env; set +a를 빠뜨리면 GitLab 주소와 백업 설정이 사라진 채로 뜬다. 백업 설정이 틀리면 API가 아예 뜨지 않는다(의도된 동작) — logs api에서 이유를 본다.

확인

  • curl -s -o /dev/null -w '%{http_code}\n' localhost:8181/users/sign_in이 200이다(포트포워딩 살아 있음)
  • API 로그에 백업 모듈 준비 완료 destination=localhost:9000 bucket=nullus-backup가 있다

CI/CD

07

CI/CD 템플릿 고르기

코드 기준

CI/CD 템플릿은 미리 들어 있다. 따로 "설치"할 것은 없고 하나를 골라 파이프라인 설정으로 넘어간다.

  1. 왼쪽 메뉴 CI/CD 템플릿을 연다(admin·devops에게만 보인다).
  2. Nullus Sample App — Backend 카드에서 기본 템플릿 사용을 누른다.
  3. Pipeline 설정 화면으로 넘어간다.
템플릿id만들어지는 앱
Nullus Sample App — Backendnullus-sample-backend-v1nginx 자리표시자 이미지 (가장 빠르다)
Nullus Sample App — Frontendnullus-sample-frontend-v1React 19 + Vite 앱
User Custom Pipelineweb-backend-v1nginx 자리표시자 이미지
Batch Job Pipelinebatch-job-v1nginx 자리표시자 이미지
"템플릿 생성"으로 만든 템플릿은 DB 에 저장된다목록과 아래 배포 화면에 바로 나오고, 같은 ID 로 다시 만들면 409 로 거부된다. 폼의 애플리케이션 유형은 web·backend·batch 중 하나다(파이프라인의 app_type ENUM 과 같다). 기본 템플릿을 수정하면 이름·설명·유형·기능만 바뀌고 Dockerfile 경로·환경 변수 같은 빌드 설정은 그대로 남는다. 어느 템플릿이든 저장소에 만들어지는 파일 구성은 같고, 템플릿은 화면 입력값을 채워 주는 역할을 한다.
08

파이프라인 만들고 실행

코드 기준

Pipeline 설정 화면에서 아래만 정하면 된다. 나머지 칸은 템플릿 값이 채워져 있다.

칸값설명
앱 이름demo-api소문자·숫자·하이픈. GitLab 프로젝트·Deployment·Argo CD 앱·호스트 이름이 된다

네임스페이스새 네임스페이스 demo앱이 배포될 곳

매니페스트 확인으로 미리 본 뒤 실행을 누른다. 그러면 다음이 자동으로 일어난다.

  1. GitLab에 그룹 nullus와 프로젝트 nullus/demo-api를 만든다.
  2. .gitlab-ci.yml·Dockerfile·deploy/ 매니페스트를 첫 커밋으로 올린다. 이 커밋이 첫 GitLab 파이프라인을 시작한다.
  3. CI 변수(배포 토큰 등), 이미지 pull Secret, Argo CD 저장소 Secret과 Application demo-api를 만든다.
"실행"은 GitLab 파이프라인을 만든다화면은 파이프라인을 만든 뒤 Nullus 쪽 "실행"을 한 번 더 부른다. 이 넘김이 GitLab 스택에서는 POST /projects/:id/pipeline로 main 파이프라인을 만들고, 실행 기록의 Trigger CI 단계에 파이프라인 주소를 남긴다. 생성 직후처럼 그 브랜치의 최신 파이프라인(위 2번의 스캐폴딩 커밋)이 아직 돌고 있으면 새로 만들지 않고 그 실행에 붙는다 — 같은 커밋의 배포 잡 둘이 되커밋을 밀면 둘째가 실패한다. 프로젝트가 아직 없으면 "프로비저닝이 끝나지 않았다"로 단계가 실패한다.
스택에 SonarQube 가 있으면 sast 단계가 생긴다 실측 기록 빌드와 함께 돌아 sonar-scanner 로 소스를 분석하고, Quality Gate 를 통과해야 deploy 가 돈다. 분석 토큰(SONAR_TOKEN, 가려짐)과 정책 변수는 Nullus 가 프로젝트 CI/CD 변수로 넣는다 — 스택 설치가 발급해 둔 토큰이라 따로 만들 것이 없다.

백업

실측 기록API로

full 백업은 플랫폼 DB · Keycloak DB · OpenBao · 스택 네임스페이스 리소스 · 볼륨(PVC)을 모두 담는다. 볼륨을 담는 동안 스택의 Deployment·StatefulSet을 0으로 내렸다가 되돌리므로 그 사이 스택이 멈춘다. SonarQube의 분석 결과는 스택 PostgreSQL의 sonarqube DB에, 검색 색인은 자기 볼륨에 있어 같은 백업에 함께 담긴다.

13

복구 후 배선

코드 기준수동

복구된 Service는 새 ClusterIP를 받는다. 그런데 러너와 Argo CD는 설치 때의 게이트웨이 주소를 hostAliases로 박아 두었고, kind 노드의 /etc/hosts도 옛 주소를 가리킨다. 그대로 두면 CI가 gitlab.nullus.local에 닿지 못하고 앱이 이미지를 받지 못한다.

터미널
NEW_IP=$(kubectl --context $CTX -n $NS get svc -l gateway.envoyproxy.io/owning-gateway-name \
  -o jsonpath='{.items[0].spec.clusterIP}')
echo "$OLD_IP -> $NEW_IP"

# 1) kind 노드 /etc/hosts (runbook 의 노드 배선과 같은 방식)
for node in $(kind get nodes --name nullus-platform); do
  for host in gitlab.$DOMAIN registry.$DOMAIN; do
    docker exec "$node" sh -c "grep -v ' $host\$' /etc/hosts > /tmp/h && cat /tmp/h > /etc/hosts && rm -f /tmp/h; echo '$NEW_IP $host' >> /etc/hosts"
  done
done

# 2) hostAliases 에 옛 주소를 가진 워크로드 (러너·Argo CD)
for w in $(kubectl --context $CTX -n $NS get deploy,sts -o json \
    | jq -r --arg old "$OLD_IP" '.items[] | select([.spec.template.spec.hostAliases[]?.ip] | index($old)) | "\(.kind|ascii_downcase)/\(.metadata.name)"'); do
  kubectl --context $CTX -n $NS get "$w" -o json \
    | jq --arg old "$OLD_IP" --arg new "$NEW_IP" \
        '.spec.template.spec.hostAliases |= map(if .ip == $old then .ip = $new else . end)' \
    | kubectl --context $CTX -n $NS replace -f -
done

# 3) 러너 설정(ConfigMap) 안의 주소
for cm in $(kubectl --context $CTX -n $NS get cm -o json \
    | jq -r --arg old "$OLD_IP" '.items[] | select((.data // {}) | tostring | contains($old)) | .metadata.name'); do
  kubectl --context $CTX -n $NS get cm "$cm" -o json | sed "s/$OLD_IP/$NEW_IP/g" \
    | kubectl --context $CTX -n $NS replace -f -
done
kubectl --context $CTX -n $NS rollout restart deploy/gitlab-runner   # 이름이 다르면 get deploy 로 러너를 찾는다

# 4) 맥에서 도구를 여는 라우터와 GitLab 포트포워딩
./scripts/port-forward-gateway.sh
curl -s -o /dev/null -w '%{http_code}\n' localhost:8181/users/sign_in   # 200. 6단계의 반복문이 다시 붙는다

# 5) API 캐시를 비운다 (환경 파일을 먼저 읽힌다)
set -a; source ~/.nullus-api.env; set +a
./scripts/runbook_local.sh refresh

확인

  • https://gitlab.nullus.local과 https://argocd.nullus.local이 다시 열린다
  • https://sonarqube.nullus.local에 백업 전 비밀번호로 로그인되고, 부록 B에서 분석했다면 그 프로젝트가 남아 있다 코드 기준
  • kubectl --context $CTX -n $NS get deploy,sts -o json | grep -c "$OLD_IP"가 0이다

  -o jsonpath='{.items[0].spec.clusterIP}')
CA_NS=$(kubectl --context $CTX get secret -A \
  -o jsonpath="{range .items[?(@.metadata.name=='nullus-internal-ca')]}{.metadata.namespace}{'\n'}{end}" | head -1)
kubectl --context $CTX -n "$CA_NS" get secret nullus-internal-ca -o jsonpath='{.data.tls\.crt}' \
  | base64 -d > /tmp/nullus-internal-ca.crt

for node in $(kind get nodes --name nullus-platform); do
  for host in gitlab.$DOMAIN registry.$DOMAIN; do
    docker exec "$node" sh -c "grep -v ' $host\$' /etc/hosts > /tmp/h && cat /tmp/h > /etc/hosts && rm -f /tmp/h; echo '$GW_IP $host' >> /etc/hosts"
  done
  docker cp /tmp/nullus-internal-ca.crt "$node:/usr/local/share/ca-certificates/nullus-internal-ca.crt"
  docker exec "$node" update-ca-certificates
  docker exec "$node" systemctl restart containerd
done
kubectl --context $CTX wait --for=condition=Ready nodes --all --timeout=180s

SonarQube 쓰기

실측 기록 (설치·수동 분석)코드 기준 (clone)

스택에 SonarQube가 있으면 지금은 여기까지 된다.

항목상태설명
설치된다템플릿 gitlab-argocd-sonarqube-v1을 stack-up으로 깐다(4단계). 스택 PostgreSQL 안에 전용 DB sonarqube를 만들어 쓰고, 그래서 스택 백업에 함께 담긴다
관리자 계정된다설치가 admin/admin을 바꿔 둔다. 비밀번호는 Secret nullus-sonarqube-credentials의 admin-password(5단계)이고, 연결 정보 창도 이 Secret을 가리킨다
Keycloak 로그인된다SonarQube Community는 SSO로 SAML만 받는다. 설치가 Keycloak에 SAML 클라이언트를 등록하고 렐름 서명 인증서를 SonarQube에 넣어, 로그인 화면에 Keycloak 버튼이 생긴다. 처음 들어온 사용자는 일반 사용자(sonar-users)로 만들어지고 로그인 ID 뒤에 숫자가 붙는다(SonarQube의 외부 계정 규칙). 관리는 admin 계정으로 한다. Keycloak 렐름 키를 회전하면 SonarQube 단계를 다시 돌려야 새 인증서를 받는다
설치 화면에서 고르기된다설치 마법사 Security 탭에서 Static Analysis (SAST) = SonarQube 를 고른다. 템플릿 gitlab-argocd-sonarqube-v1을 고르면 미리 채워진다. 다만 화면 설치는 kind 노드 배선을 하지 않으므로 부록 A 를 따른다
파이프라인 분석·차단된다파이프라인에 sast 단계가 생긴다(GitLab · GitHub Actions · Jenkins). 기본은 Quality Gate 실패 시 차단이고, 아래처럼 스택 정책으로 경고로 바꾼다. SonarQube 에 닿지 못하면 이미지 스캔과 같은 장애 정책(on_scanner_unreachable)을 따른다
결과 화면된다CI/CD 목록 → 파이프라인 → History 에서 실행마다 SAST 판정(통과 · 경고 · 차단 · 분석 실패)이 붙고, 실행을 고르면 통과하지 못한 조건 · 지표 · SonarQube 링크가 보인다. sast 잡이 남긴 sast-report.json 을 실행 기록 동기화가 읽어 만든다 실측 기록

정책을 경고로 바꾸기. Quality Gate 를 막 들인 팀이 기존 코드의 문제로 배포가 멈추지 않게 하려면 스택 정책을 바꾼다. 저장하면 그 스택의 파이프라인 변수(NULLUS_SAST_ON_GATE_FAILURE)에 바로 실리고, 다음 실행부터 따른다(실측: 같은 커밋을 다시 돌리자 sast 가 "경고 정책에 따라 통과" 로 끝나고 deploy 가 돌았다).

스택 정책
curl -s -X PUT $API/api/v1/stacks/$STACK_ID/image-scan-policy -H 'Content-Type: application/json' \
  -d '{"block_severity":"CRITICAL","ignore_unfixed":true,"on_scanner_unreachable":"block","sast_on_gate_failure":"warn"}' \
  | jq '{policy, pushes}'                        # 되돌리려면 "block"

손으로 분석 돌려 보기(선택). 파이프라인 밖에서 확인하고 싶을 때 쓴다. 8단계에서 만든 앱 저장소를 받아 스캐너 컨테이너로 분석한다. SonarQube에는 포트포워딩으로 붙는다. 로컬 MinIO가 9000을 쓰므로 19000으로 연다.

① 분석 토큰
source ~/.nullus-e2e.env
SQ_PW=$(kubectl --context $CTX -n $NS get secret nullus-sonarqube-credentials \
  -o jsonpath='{.data.admin-password}' | base64 -d)
kubectl --context $CTX -n $NS port-forward svc/sonarqube 19000:9000 >/dev/null 2>&1 &
SQ_TOKEN=$(curl -s -u "admin:$SQ_PW" -X POST http://localhost:19000/api/user_tokens/generate \
  --data-urlencode "name=e2e-$(date +%s)" -d type=GLOBAL_ANALYSIS_TOKEN | jq -r .token)
echo "${SQ_TOKEN:0:4}"                        # sqa_ 로 시작하면 된다
② 앱 저장소 받기
# 내부 CA 는 5단계의 setup-local-domain.sh 가 꺼내 둔 것. 사용자 root 와 5단계 비밀번호를 묻는다
git -c http.sslCAInfo=$PWD/.runbook-logs/nullus-internal-ca.crt \
  clone https://gitlab.$DOMAIN/nullus/$APP.git ~/$APP
③ 분석
# 스캐너 이미지는 amd64 만 있다. Apple Silicon 에서는 에뮬레이션으로 돈다(30초 남짓)
docker run --rm --platform linux/amd64 -v ~/$APP:/usr/src \
  -e SONAR_HOST_URL=http://host.docker.internal:19000 -e SONAR_TOKEN=$SQ_TOKEN \
  sonarsource/sonar-scanner-cli:12.2 -Dsonar.projectKey=$APP -Dsonar.qualitygate.wait=true
echo "exit=$?"

curl -s -u "admin:$SQ_PW" "http://localhost:19000/api/qualitygates/project_status?projectKey=$APP" \
  | jq -r '.projectStatus.status'

확인

  • 스캐너가 QUALITY GATE STATUS: PASSED와 EXECUTION SUCCESS로 끝나고 exit=0이다
  • https://sonarqube.nullus.local/dashboard?id=demo-api에 프로젝트와 이슈가 보인다
첫 분석은 문제가 있어도 통과한다기본 Quality Gate(Sonar way)는 "새 코드" 조건만 본다. 첫 분석에는 비교할 기준이 없어서, 실측에서 eval을 CRITICAL로 잡고도 PASSED였다. 그 뒤 분석에서 새 문제가 하나라도 생기면 new_violations로 FAILED가 되고, 스캐너가 EXECUTION FAILURE와 종료 코드 3으로 끝난다. 파이프라인 잡을 멈추는 것은 이 종료 코드다 — 실제 파이프라인에서도 첫 실행은 통과했고, eval 을 넣은 커밋에서 sast 가 실패하고 deploy 가 건너뛰어졌다.

컨테이너 이미지 취약점은 SonarQube가 아니라 Trivy가 본다. stack-up --template=gitlab-harbor-trivy-v1로 깔면 스택에 Trivy가 들어가고 파이프라인에 차단 게이트(image-scan 잡)가 붙는다. 소스 정적 분석(SAST)은 아니다.

끝나면 포트포워딩을 닫는다: pkill -f 'port-forward svc/sonarqube'
