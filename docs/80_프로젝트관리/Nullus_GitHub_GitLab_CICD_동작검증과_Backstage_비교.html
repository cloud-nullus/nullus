GitHub 기반과 GitLab 기반은 실제로 동작하는가

앞선 「Nullus CI/CD 구현 학습 가이드」가 internal/cicd/ 모듈의 내부 로직을 다뤘다면, 이 문서는 한 층 위의 질문에 답한다 — Golden Path로 제공되는 GitHub 조합과 GitLab 조합이 실제로 어디까지 동작하는가, 그리고 같은 문제 영역의 대표 도구인 Backstage와 동작 방식이 어떻게 다른가.

모든 판단은 저장소 코드·마이그레이션·테스트·CHANGELOG에서 확인한 사실에 근거한다. "카탈로그에 있다"와 "실제로 설치·실행된다"를 구분하는 것이 이 문서의 목적이다.

0. 3줄 결론

세부 근거는 5장·6장에 있다. 먼저 결론부터 본다.

GitLab 기반
설치 엔진 실장 · verified

설치 엔진이 실제로 붙어 있는 유일한 경로다. GitLab 차트 설치, Runner 등록 토큰 자동 발견, 오브젝트 스토리지 버킷 사전 생성, DB Secret 연결, Keycloak OIDC 클라이언트 자동 등록까지 코드가 존재한다. 호환성 매트릭스 상태도 verified다. 다만 리소스가 무거워 단일 노드 Kind에서는 15분 안에 완료되지 않았고, CHANGELOG에 설치 실패–수정 이력이 길게 남아 있다.

GitHub 기반
설치할 것이 거의 없음 · untested

GitHub와 GitHub Actions는 external로 선언되어 클러스터에 아무것도 설치되지 않는다. 그래서 설치는 빠르게 성공하지만(Kind 로컬 4분 5초 통과), 조합이 선언한 컨테이너 레지스트리 Harbor는 설치 DAG에 스텝 자체가 없어 설치되지 않는다. 호환성 상태는 untested·전 도구 beta라 배포하려면 acknowledge_warnings: true가 필요하다. 에어갭 환경에서는 구조적으로 불가능하다.

공통
파이프라인 자체는 자동화 대상 아님

두 경로 모두 .gitlab-ci.yml이나 GitHub Actions 워크플로를 생성하는 코드가 없고, Argo CD Application 리소스를 만드는 코드도 없다. Nullus 스택 모듈은 "도구를 설치"할 뿐 "파이프라인을 정의·실행"하지 않는다. 애플리케이션 배포는 별도 경로인 internal/cicd/ 모듈이 Argo CD를 거치지 않고 매니페스트를 직접 apply하는 방식으로 처리한다.

이 결론을 어떻게 읽어야 하나 "동작하지 않는다"가 아니라 "자동화 경계가 도구 설치까지"라는 뜻이다. PRD에서 Nullus의 가치는 "Day 0 — 검증된 도구 조합을 즉시 설치"로 정의되어 있고, 코드는 그 정의에 충실하다. 문제는 UI와 카탈로그가 그보다 넓은 범위를 약속하는 것처럼 보인다는 점이다(6장).

1. 구조적 차이 — 설치형 vs 외부 연동형

두 Golden Path는 같은 카탈로그에 나란히 놓여 있지만, 실행 모델이 근본적으로 다르다. 이 차이를 먼저 잡아야 이후 모든 관찰이 설명된다.

GitLab 조합 — 클러스터 안으로 다 들어온다

[ 사용자 K8s 클러스터 ]
  ├─ GitLab CE      ← Nullus가 helm 설치
  ├─ GitLab CI      ← GitLab에 내장
  ├─ GitLab Runner  ← Nullus가 helm 설치 + 토큰 자동 등록
  ├─ GitLab Registry← GitLab에 내장
  ├─ MinIO / PostgreSQL ← GitLab의 백엔드
  ├─ Argo CD        ← Nullus가 helm 설치
  └─ Prometheus / Grafana / Loki

인터넷 없이도 성립한다. 에어갭 번들에 GitLab CNG 이미지 15종이 포함되어 있다.

GitHub 조합 — 핵심이 클러스터 밖에 있다

[ 외부 SaaS ]
  ├─ GitHub          ← Nullus 관여 없음
  └─ GitHub Actions  ← Nullus 관여 없음

[ 사용자 K8s 클러스터 ]
  ├─ Harbor       ← 카탈로그에만 존재, 설치 스텝 없음
  ├─ MinIO
  ├─ Argo CD      ← Nullus가 helm 설치
  └─ Prometheus / Grafana

인터넷과 GitHub 계정이 전제다. 에어갭에서는 성립하지 않는다.

핵심 판별식 — version == "external" 카탈로그에서 GitHub 계열 도구는 HelmVersion: "external", AppVersion: "external"로 표기된다. 이 문자열 하나가 설치 엔진 전체의 분기를 좌우한다. 다음 장에서 그 게이팅 코드를 본다.

2. 설치 DAG 게이팅 — 어떤 스텝이 켜지고 꺼지는가

스택 설치는 internal/stack/usecase/install_stack.go의 installDAG(21스텝)를 위상 정렬로 실행한다. 각 스텝에는 "이 스텝을 켤 것인가"를 판정하는 조건 함수가 붙어 있고, 그 판정에 GitLab/GitHub 구분이 들어온다.

판별 함수 (orchestrator.go:444, 458)

func isGitLabSourceRepositorySelection(sel domain.ToolSelection) bool {
    if !sel.Enabled { return false }
    if strings.EqualFold(strings.TrimSpace(sel.Version), "external") {
        return false          // ← GitHub은 여기서 걸러진다
    }
    name := normalizeToolName(sel.Name)   // 소문자 + 공백/언더바 → 하이픈
    if name == "" { return true }   // 이름이 비면 관대하게 true
    return name == "gitlab" || name == "gitlab-ce"
}

func isGitLabCISelection(sel domain.ToolSelection) bool {
    // 동일한 구조, 마지막 비교만 다르다
    return name == "gitlab-ci" || name == "gitlab-runner"
}

세 겹의 방어가 있다 — Enabled 여부 → version이 external인지 → 이름이 GitLab 계열인지. CHANGELOG에 남은 #56 "GitHub 선택 시 GitLab이 함께 설치되던 문제"가 바로 이 이름 기준 판정이 없어서 생긴 버그였고, 반대로 #85 "GitLab CE 표기 시 GitLab 설치 단계를 건너뛰던 문제"는 판정이 지나치게 엄격해서 생긴 버그였다. 현재 코드는 그 두 사고의 결과물이다.

건너뛴 스텝도 completed = true로 표시된다. 그래서 provisioning_sso가 installing_object_storage_buckets에 의존하더라도 GitHub 조합에서 교착이 생기지 않는다. "스킵도 성공"이라는 이 규칙이 GitHub 조합의 설치가 빠르게 끝나는 직접적 이유다.

3. GitLab 경로 심층 — 실제로 구현된 것들

GitLab은 Nullus가 설치·구성까지 책임지는 유일한 CI 플랫폼이다. 구현 밀도가 높다.

차트 설치

gitlab 차트를 https://charts.gitlab.io/에서 설치한다. 기본 pin은 8.7.2이며, DB 테이블 stack_helm_step_configs에 항목이 있으면 그 값이 우선한다 (chartSpecForStep의 메타데이터 우선 조회).

Runner 차트

gitlab-runner 차트 0.72.0. GitLab 설치 완료를 deps로 요구한다 (installing_runner depends on installing_gitlab).

Runner 등록 토큰 자동 발견 — 가장 손이 많이 간 부분

GitLab Runner를 등록하려면 GitLab 인스턴스에서 토큰을 꺼내야 한다. API가 아니라 toolbox 파드에서 Rails 콘솔을 실행해 가져온다. 

kubectl -n {ns} exec deploy/gitlab-toolbox -c toolbox -- bash -lc \
  "gitlab-rails runner '{script}'"

// 1차 시도 — 신형 runner 객체 (없으면 생성)
runner = Ci::Runner.where(description: "nullus-shared-runner", runner_type: :instance_type)
                   .order(id: :desc).first
runner ||= Ci::Runner.create!(description: "nullus-shared-runner",
                              runner_type: :instance_type, run_untagged: true, locked: false)
puts runner.token.to_s

// 2차 폴백 — 구형 등록 토큰
puts ApplicationSetting.current.runners_registration_token

최대 24회 × 10초 = 4분간 재시도한다. 재시도 대상 에러 문자열 목록이 흥미롭다 — container not found, unable to upgrade connection, pods "gitlab-toolbox" not found, application_settings, pg::undefinedtable.

이 재시도 목록이 말해 주는 것 pg::undefinedtable과 application_settings가 재시도 힌트에 있다는 것은, GitLab 마이그레이션이 아직 안 끝난 상태에서 Rails 콘솔을 두드린 경험이 있었다는 뜻이다. 분산 시스템에서 "설치 완료"와 "사용 가능"이 다르다는 것을 보여 주는 실전 사례다. 토큰 파싱도 방어적이다 — 출력 줄 중 Defaulted container로 시작하거나 공백이 포함된 줄을 버리고 마지막 줄을 택한다.

GitLab 전용 사전 준비 단계

오브젝트 스토리지

installing_object_storage_secret + _buckets로 MinIO에 GitLab용 버킷을 미리 만들어 둔다. CHANGELOG #70에서 추가된 단계로, GitLab 설치의 선행 조건이다.

DB Secret 연결

GitLab values의 global.psql.password.secret이 provisioning_secrets가 만든 Secret 이름과 같은 상수(ProvisionedPostgresSecret)를 가리키도록 맞춰져 있다. 어긋나면 실패하는 테스트가 붙어 있다.

SSO 클라이언트

provisioning_sso가 Keycloak에 gitlab OIDC 클라이언트를 등록한다. 콜백 /users/auth/openid_connect/callback, PKCE S256, 스택 슬러그로 clientId를 네임스페이싱해 다중 스택 충돌을 막는다.

SSO 자동 등록 대상은 gitlab · grafana · argocd · harbor · minio 다섯이다. GitHub은 외부 IdP를 쓰므로 목록에 없다.

토큰 회전 후 재시작 정책

// internal/admin/rotation/restart.go
//   - GitLab Runner: config.toml 을 기동 시 1회만 렌더링 → 재시작 필요
//   - ArgoCD repository Secret: 매 요청 시점에 읽음 → 재시작 불필요
var restartRequiredProviders = map[string]bool{
    "gitlab": true, "gitlab-ce": true, "gitlab-ci": true,
    "gitlab-runner": true, "gitlab-registry": true,
    "postgresql": true, "minio": true, "harbor": true, "grafana": true,
    "argocd": false, "argo-cd": false,
}

시크릿을 회전해도 소비자가 설정을 언제 읽느냐에 따라 재시작 필요 여부가 갈린다는 통찰이 코드에 명시적으로 담겨 있다. 모르는 provider는 재시작하지 않는다 — "불필요한 재기동이 더 위험하다"는 주석이 붙어 있다.

4. GitHub 경로 심층 — 무엇이 없는가

GitHub 조합에서 Nullus가 하는 일은 사실상 Argo CD와 모니터링 스택을 설치하는 것뿐이다. GitHub 관련 런타임 코드는 스택 모듈 전체에 존재하지 않는다 — 카탈로그 항목, 호환성 매트릭스 항목, 테스트 픽스처가 전부다.

e2e 테스트가 스스로 인정하는 범위

// e2e/golden_path_kind_test.go
{
    templateID: "github-argocd-v1",
    toolOverrides: func(cfg *domain.StackConfig) {
        // GitHub + GitHub Actions are external SaaS — skip entirely.
        cfg.Artifacts.SourceRepository.Enabled = false
        cfg.Pipeline.CIPlatform.Enabled = false
        ...
    },
},

테스트 자체가 GitHub과 Actions를 Enabled = false로 끄고 시작한다. 즉 "GitHub 골든패스의 e2e 검증"이 검증하는 것은 GitHub이 아니라 Argo CD + 스토리지 설치다. 이건 테스트의 결함이 아니라 설계의 정직한 반영이다 — 클러스터에서 검증할 수 있는 부분이 그것뿐이다.

Harbor는 카탈로그에만 있고 설치되지 않는다 github-argocd-v1은 container_registry: Harbor 1.15.0/2.11.0을 선언한다. 그런데 저장소 전체에서 installing_harbor는 Keycloak SSO 클라이언트 스펙과 그 테스트에만 등장하고, installDAG에도 orderedStep에도 없다. Harbor 차트를 설치하는 코드가 제품 설치 엔진에 없다.
  • 있는 것: 리소스 추정치(calculate_resources.go: 2 vCPU / 4Gi / 40Gi), 표시 이름 매핑, SSO 클라이언트 스펙
  • 없는 것: Helm 차트 스펙, 설치 스텝, DAG 노드
  • 예외: 에어갭 번들의 별도 셸 스크립트 airgap/scripts/27-install-stacks.sh에는 Harbor 1.15.0 항목이 있다 — 제품 설치 엔진이 아닌 오프라인 설치 경로다
결과적으로 GitHub 조합을 선택하면 이미지를 올릴 레지스트리 없이 스택이 완성된다.

Pre-Deploy Gate 판정

배포 전 서버 측 게이트가 호환성 매트릭스를 재평가한다(runPreDeployGate). github-argocd-v1의 매트릭스 상태는 untested다.

warn인데 명시적 승인이 없으면 DEPLOY_COMPAT_WARN_UNACK로 배포가 차단된다. 즉 GitHub 조합은 "경고를 읽고 동의했다"는 선택을 거쳐야만 설치가 시작된다. 이건 설계 의도대로 동작하는 것이다.

아키텍처 검사에서의 비대칭

applyArchCheck의 정책은 매트릭스 상태에 따라 다르다.

  • verified 매트릭스 + arch 불일치 → fail (하드 블록) — 도구를 바꾸거나 노드 풀을 추가해야 한다
  • untested 매트릭스 + arch 불일치 → warn으로만 강등 — 이미 미검증이므로 승인으로 넘어갈 수 있다

그래서 arm64 노드가 섞인 클러스터에서, GitLab 조합은 매트릭스에 arm64가 반영되어 있지 않으면 배포가 완전히 막히고, GitHub 조합(Harbor amd64-only)은 경고로 통과한다. 다음 장의 드리프트 이슈와 직결된다.

5. 검증 근거 — 실제로 어디까지 확인됐나

"잘 동작하는가"에 대한 답은 추측이 아니라 저장소에 남은 검증 기록에서 나온다.

이 목록은 부정적 신호가 아니다. GitLab 경로만 이렇게 긴 수정 이력을 가진 이유는 그 경로만 실제로 끝까지 실행되기 때문이다. 실행되지 않는 코드는 버그 리포트를 만들지 않는다.

UI·카탈로그·API 응답이 약속하는 것과 실제 코드가 하는 것 사이의 간극을 한자리에 모았다. 각 항목은 소스에서 확인한 사실이다.

따라서 "Nullus로 GitOps 파이프라인을 구축한다"는 서술은 현재 코드 기준으로는 "GitOps 도구를 설치해 준다"까지가 정확하다. 도구와 앱을 잇는 배선은 사용자가 만든다.

7. 토큰 회전 — 구현과 배선이 갈리는 지점

GitLab과 GitHub 양쪽 모두 토큰 재발급 구현체가 존재한다. 그리고 양쪽 모두 배선되어 있지 않다. 구현 방식 자체가 두 플랫폼의 인증 모델 차이를 잘 보여 주므로 함께 본다.

GitLabReissuer — PAT 자기 회전

POST {base}/personal_access_tokens/self/rotate
Header: PRIVATE-TOKEN: {현재 토큰}
→ { "token": "새 토큰" }

현재 토큰이 자기 자신을 갱신한다. 기본 base는 https://gitlab.com/api/v4. 지원 provider: gitlab, gitlab-ce, gitlab-ci, gitlab-registry.

GitHubReissuer — App 설치 토큰 발급

// 1) App 개인키(RSA)로 JWT 서명 (RS256, 9분 유효)
{ iat: now-30s, exp: now+9m, iss: appID }

// 2) JWT로 설치 토큰 요청
POST {api}/app/installations/{id}/access_tokens
Header: Authorization: Bearer {appJWT}
        X-GitHub-Api-Version: 2022-11-28
→ { "token": "설치 액세스 토큰" }

현재 토큰이 필요 없다. App 개인키만 있으면 언제든 새로 발급한다. 메타데이터에 app_id, installation_id, private_key_pem이 필요하다.

그런데 라우터가 비어 있다

// cmd/api/main.go — 토큰 회전 스케줄러 기동
go adminscheduler.NewTokenRotationScheduler(
    pool, secretRouter, tokenRotationInterval(), 0, slog.Default(),
    rotation.NewRouterReissuer(),   // ← 갓 만든 빈 라우터. Register() 호출 없음
).WithRestarter(
    adminrepo.NewClusterWorkloadRestarter(kubeconfigProvider),
).Start(rotationCtx)

NewGitLabReissuer와 NewGitHubReissuer는 운영 코드 어디에서도 호출되지 않는다. 라우터가 비어 있으므로 모든 Reissue()가 ErrReissueUnsupported를 반환한다.

그 결과 무슨 일이 벌어지나

스택 설치가 토큰 소스를 등록한다 BuildStackTokenSourceInputs가 source_repository / container_registry / ci_platform / cd_tool 네 개를 TokenType: "reissue"로 등록한다. 값은 비워 두고 경로만 잡는다 (kv/nullus/{env}/{org}/{module}/{provider}/token).
스케줄러가 만기 도래 항목을 집는다 next_check_at <= now()인 token_sources 행을 최대 100건 조회.
재발급을 시도하지만 지원되지 않는다 issueToken()이 type == "reissue"이므로 라우터를 호출 → ErrReissueUnsupported.
무작위 토큰으로 폴백한다 
if err != nil && err != rotation.ErrReissueUnsupported {
    return "", err
}
return randomToken()   // "nls_" + 24바이트 hex
지원되지 않는 경우는 에러로 취급하지 않고 무작위 문자열을 만들어 OpenBao에 기록한다.
성공으로 기록하고 소비자를 재시작한다 status='rotated', ROTATION_SUCCESS 이벤트 기록, RequiresRestart("gitlab")==true이므로 GitLab Runner를 rolling restart.
주의해서 읽어야 할 대목 플랫폼이 스스로 발급하는 시크릿(PostgreSQL·MinIO 비밀번호 등)에는 무작위 토큰이 올바른 동작이다. 반면 GitLab PAT나 GitHub App 토큰처럼 외부 provider가 발급 주체인 자격증명에 무작위 문자열을 쓰면 인증이 깨진다. type = "reissue"라는 표시는 바로 그 구분을 위해 존재하는데, 라우터가 비어 있어 그 구분이 무력화된 상태다.

단, 이 경로는 authentication.provider == "openbao"이고 OpenBao 시크릿 스토어가 등록된 스택에서만 동작한다 (runIteration 첫 줄의 s.secret.Has("openbao") 가드). 모든 설치에 해당하지는 않는다.

고치는 방법은 usecase 수정이 아니라 배선 추가다 — router.Register("gitlab", rotation.NewGitLabReissuer(baseURL)) 형태로 등록하면 된다. 7장의 두 구현체는 그대로 쓸 수 있다.

3계층 드리프트 — 코드가 스스로 경고한 문제

memory_compatibility.go에는 다음 주석이 달려 있다. 

// If this function drifts from the DB state, the Pre-Deploy Gate will
// produce different verdicts in tests vs. real deployments.

그리고 실제로 arm64 지원에서 드리프트가 발생해 있다.

① 인메모리 상수

GitLab 계열이 archAMD64Only(amd64만).
테스트가 이 값을 본다.

② DB 시드

마이그레이션 000048_expand_gitlab_arm64_support가 gitlab-allinone-v1·gitlab-argocd-v1의 source/ci/registry를 ["amd64","arm64"]로 갱신.

③ 런타임이 보는 것

main.go는 NewPostgresCompatibilityRepository를 주입한다. 즉 DB(②)가 실제 판정 기준이고, 인메모리(①)는 테스트 전용이다.

실질적 귀결 arm64 노드가 있는 클러스터에서 GitLab 조합은 실제 배포 시 통과한다(DB에 arm64가 반영됨). 하지만 인메모리 매트릭스를 쓰는 단위 테스트에서는 verified + arch 불일치 = fail 판정이 나온다. 코드 주석이 예고한 "테스트와 실배포의 판정이 갈리는" 상황이 그대로 발생한 사례다.

참고로 마이그레이션 000048은 github-argocd-v1을 갱신 대상에서 제외했다. 그 조합의 Harbor는 여전히 amd64-only이지만, 매트릭스가 untested라 arch 불일치가 fail이 아닌 warn으로 처리된다(4장).

9. Backstage란 무엇이고, 저장소에서 어떤 위치인가

먼저 사실 확인 이 저장소에는 Backstage 관련 코드가 한 줄도 없다. Go·TypeScript·YAML 어디에도 backstage 문자열이 없고, 등장하는 곳은 docs/10_제품기획/, docs/70_전략/ 등 기획·전략 문서뿐이다. 따라서 이 장의 비교는 "구현 대 구현"이 아니라 "실행 모델 대 실행 모델"이다.

Backstage의 실행 모델 요약

Backstage(Spotify 개발, CNCF)는 개발자 포털을 만들기 위한 프레임워크다. 완제품이 아니라 뼈대다. 핵심 구성은 셋이다.

Software Catalog

서비스·API·리소스·팀을 catalog-info.yaml(Entity)로 선언하고, Git 저장소를 스캔해 수집한다. "우리 조직에 무엇이 있는가"의 단일 인덱스.

Software Template (Scaffolder)

템플릿을 실행하면 새 저장소를 만들고 보일러플레이트·CI 설정·카탈로그 항목을 함께 생성한다. Day 0의 "새 서비스 시작"을 표준화한다.

Plugin

기능 확장은 React/Node 코드를 작성해 포털에 붙인다. Argo CD·Kubernetes·Jenkins 플러그인 등이 그렇게 만들어진다.

핵심은 Backstage가 인프라를 만들지 않는다는 점이다. 이미 존재하는 시스템을 발견·표시·연결하고, 새 코드베이스를 스캐폴딩한다.

상태의 원천 PostgreSQL(스택·설치 이력) + 실제 클러스터 상태 Git의 catalog-info.yaml(선언이 원천, 포털은 캐시)
확장 방법 데이터 — Golden Path 항목과 Helm 스텝 메타데이터를 추가 코드 — 플러그인(React/Node)을 작성해 빌드에 포함
확장 비용 새 도구를 추가하려면 설치 스텝·values·리소스 추정을 코드에 넣어야 함 플러그인 개발·유지 인력이 상시 필요 (프레임워크 특성)
사용자 DevOps 엔지니어 (도구를 설치하는 사람) 애플리케이션 개발자 (서비스를 찾고 시작하는 사람)
시간축 Day 0 — 아무것도 없는 상태에서 파이프라인 구축 Day 1–2 — 구축된 것을 조직에 노출·운영
K8s 의존 필수 (설치 대상이 클러스터) 선택적 (포털은 어디서든 뜬다)
도구 버전 관리 호환성 매트릭스로 검증된 조합만 제시하고 게이트로 차단 해당 개념 없음 — 무엇을 쓸지는 조직이 결정
에어갭 이미지·차트 번들로 오프라인 설치 지원 포털 자체는 가능하나 플러그인·스캐폴딩이 외부 Git/레지스트리에 의존
GitHub / GitLab 취급 GitLab은 설치 대상, GitHub은 외부 전제 — 비대칭 둘 다 동등한 연동 대상 (Integration 설정으로 스캔·스캐폴딩)
가장 큰 차이 한 가지만 꼽으면 Backstage는 GitHub/GitLab을 대칭적으로 다루고, Nullus는 그럴 수 없다. Backstage에게 두 플랫폼은 모두 "API로 읽고 쓰는 외부 시스템"이라 Integration 설정만 바꾸면 된다. Nullus는 도구를 클러스터에 설치하는 엔진이므로, 설치 가능한 GitLab과 설치 불가능한 GitHub이 구조적으로 다른 취급을 받을 수밖에 없다. 2장의 게이팅 함수가 그 비대칭의 코드 표현이다.

11. 흐름 나란히 보기 — "새 서비스를 시작한다"

같은 목표를 두 도구가 어떻게 다르게 처리하는지 단계별로 비교한다.

Backstage — Software Template 실행

  1. 개발자가 포털에서 "Node.js Service" 템플릿 선택
  2. 폼에 서비스명·소유 팀·저장소 위치 입력
  3. Scaffolder가 새 Git 저장소를 생성하고 보일러플레이트 커밋
  4. CI 설정 파일(.github/workflows/*.yml 등)을 함께 생성
  5. catalog-info.yaml을 만들어 카탈로그에 자동 등록
  6. 이후 포털에서 이 서비스의 CI 상태·문서·의존성을 한눈에 확인

전제: CI 플랫폼과 클러스터가 이미 존재한다.

Nullus — 스택 설치 + CI/CD 파이프라인 생성

  1. DevOps가 UI에서 Golden Path 선택 (GitLab All-in-One 등)
  2. 호환성 게이트 통과 (warn이면 명시적 승인)
  3. 설치 엔진이 21스텝 DAG를 실행해 GitLab·Argo CD·모니터링을 클러스터에 설치
  4. Keycloak OIDC 클라이언트 자동 등록, Runner 토큰 자동 발견
  5. (별도 모듈) 개발자가 6단계 위저드로 파이프라인 정의 후 배포
  6. 매니페스트를 client-go로 직접 apply, 진행 상황을 스텝 단위로 표시

전제: 빈 쿠버네티스 클러스터 하나. 산출: 동작하는 도구 스택.

시간축으로 겹쳐 보면 두 도구는 경쟁하지 않는다

  빈 클러스터 ──▶ 도구 스택 구축 ──▶ 서비스 개발/운영 ──▶ 조직 규모 확대
                 └──── Nullus ────┘
                                    └────── Backstage ──────┘

  Nullus 가 만든 결과물(GitLab, Argo CD, Harbor…)이
  Backstage 카탈로그의 입력이 된다.

저장소의 경쟁 분석 문서도 같은 결론에 도달한다 — "직접 경쟁하기보다 보완 관계". Backstage는 "구축된 서비스의 카탈로그화"를 담당하고, Nullus는 "아직 아무것도 없는 상태에서 구축"을 담당한다.

13. 언제 무엇을 쓰나 — 판단 가이드

상황권장이유
폐쇄망·에어갭 환경 GitLab 조합 GitHub은 SaaS라 구조적으로 불가. 에어갭 번들에 GitLab CNG 이미지가 포함되어 있다
소스 관리도 사내에 두어야 하는 규제 환경 GitLab 조합 소스·CI·레지스트리가 모두 클러스터 안에 들어온다
이미 GitHub을 쓰고 있고, K8s 배포 기반만 필요 GitHub 조합 + 수동 보완 설치는 빠르지만 레지스트리(Harbor)를 별도로 준비해야 한다
단일 노드 개발 클러스터(Kind 등)에서 시험 GitHub 조합 GitLab 풀스택은 단일 노드 Kind에서 15분 내 완료되지 않은 기록이 있다
arm64 노드가 섞인 클러스터 사전 확인 필수 GitLab은 DB 시드에 arm64가 반영되어 통과하지만, 인메모리 매트릭스와 드리프트가 있다(8장)
서비스 카탈로그·문서·소유권 관리가 목적 Backstage Nullus의 문제 영역이 아니다. 도구 설치가 끝난 뒤의 과제
도구가 이미 다 깔려 있고 개발자 셀프서비스만 필요 Backstage Nullus를 도입해도 설치할 것이 없다
빈 클러스터에서 시작해 조직 규모까지 키울 계획 Nullus → Backstage 순차 시간축이 겹치지 않는다. Nullus 산출물이 Backstage 카탈로그의 입력이 된다

GitHub 조합을 실제로 쓰려면 사용자가 해야 할 일

컨테이너 레지스트리 준비Harbor가 설치되지 않으므로 GHCR·ECR 등 외부 레지스트리를 직접 지정한다
GitHub Actions 워크플로 작성Nullus가 생성해 주지 않는다. 빌드·푸시 파이프라인을 직접 만든다
Argo CD Application 정의설치된 Argo CD에 앱을 등록하는 리소스를 직접 만든다 — Nullus는 생성하지 않는다
배포 게이트에서 경고 승인untested 매트릭스이므로 acknowledge_warnings: true로 진행
모니터링 표시 한계 인지소스 저장소 항목은 파드 접두사가 gitlab로 고정되어 있어 상시 미발견으로 표시된다

14. 이해도 점검

Q1. GitHub 조합의 스택 설치가 GitLab 조합보다 훨씬 빨리 끝나는 이유는? 그것이 "더 안정적"이라는 뜻인가?
답 보기

GitHub과 GitHub Actions는 version == "external"이라 isGitLabSourceRepositorySelection/isGitLabCISelection이 false를 반환하고, installing_gitlab·installing_runner·오브젝트 스토리지 3단계가 모두 건너뛰어진다. 건너뛴 스텝은 completed = true로 표시되어 후속 의존이 즉시 풀린다. 설치할 것이 적어서 빠른 것이지 안정성 때문이 아니다. 오히려 조합이 선언한 Harbor는 설치되지도 않는다.

Q2. github-argocd-v1을 배포하려는데 400 DEPLOY_COMPAT_WARN_UNACK이 났다. 원인과 해결은?
답 보기

이 조합의 호환성 매트릭스 상태가 untested라 evaluateMatrixStatus가 warn(70점) + MATRIX_UNTESTED 이슈를 낸다. Pre-Deploy Gate는 warn 판정일 때 명시적 승인 없이는 배포를 막는다. 요청 본문에 acknowledge_warnings: true를 넣으면 진행된다. 차단이 아니라 의도된 안전장치다.

Q3. Nullus가 Argo CD를 설치했다. 그럼 CI/CD 모듈의 앱 배포는 Argo CD를 통해 이뤄지는가?
답 보기

아니다. argoproj.io/v1alpha1 Application 리소스를 만드는 코드가 저장소에 없고, internal/cicd/는 kubeconfig로 client-go dynamic client를 써서 매니페스트를 직접 apply한다. 설치된 CD 도구와 실제 배포 경로가 분리되어 있다. Argo CD는 설치만 되고 아무 앱도 동기화하지 않는 빈 상태로 남는다.

Q4. GitLab PAT를 토큰 소스로 등록해 두면 24시간마다 자동 재발급되는가?
답 보기

현재 배선에서는 아니다. GitLabReissuer는 구현되어 있지만 main.go가 빈 NewRouterReissuer()를 주입해 어떤 provider도 등록되어 있지 않다. Reissue()가 ErrReissueUnsupported를 반환하고, issueToken은 이를 에러로 취급하지 않고 randomToken()(nls_ + hex)으로 폴백한 뒤 status='rotated'로 성공 기록을 남긴다. 라우터에 Register("gitlab", ...)를 추가하면 해결된다.

Q5. Backstage와 Nullus 중 하나만 골라야 한다면? — 이 질문 자체의 문제는?
답 보기

둘은 시간축이 다르다. Nullus는 Day 0(빈 클러스터 → 도구 스택 구축), Backstage는 Day 1–2(구축된 것을 카탈로그화·포털화)를 담당한다. Nullus의 산출물(GitLab, Argo CD, 모니터링)이 Backstage 카탈로그의 입력이 된다. 저장소의 경쟁 분석 문서도 "직접 경쟁하기보다 보완 관계"로 결론짓고, v0.5에 "Nullus 설치 스택을 Backstage 카탈로그에 자동 등록"을 제언했다(미구현).

Q6. 같은 gitlab-argocd-v1인데 CI/CD 화면과 스택 화면의 버전 표기가 다르다. 어느 쪽이 실제 설치 버전인가?
답 보기

둘 다 아닐 수 있다. 표시는 Stack 모듈의 템플릿(GitLab 9.5.1/18.5.1)이 설치 기준에 가깝고 CI/CD 모듈의 Golden Path(8.7.2/17.7.2)는 표시용 카탈로그다. 그러나 런타임에는 chartSpecForStep이 stack_helm_step_configs 테이블을 먼저 조회하고, 거기 값이 있으면 그것을 쓴다. 없을 때만 코드의 기본 pin으로 폴백한다.
