CI/CD는 어떻게 구현되어 있는가

이 문서는 Nullus 저장소의 CI/CD 관련 코드를 실제 소스 기준으로 따라가며 정리한 학습자료다. 도메인 모델 → 유스케이스 → 어댑터 → HTTP → 프론트엔드 순으로, "요청 하나가 들어와서 쿠버네티스 리소스가 생기기까지" 무슨 일이 벌어지는지를 코드 경로 그대로 추적한다.

읽는 대상은 이 모듈에 처음 들어오는 개발자다. 아키텍처 원칙(Modular Monolith / Clean Architecture / DDD)이 코드에서 실제로 어떤 모양으로 나타나는지 확인하는 것이 목표다.

0. 시작하기 전에 — "CI/CD"라는 말이 두 가지를 가리킨다

이 저장소에서 CI/CD라는 단어는 서로 다른 두 대상을 가리킨다. 코드를 읽을 때 이 둘을 섞으면 바로 헷갈리므로 먼저 분리해 둔다.

① 제품 기능으로서의 CI/CD 모듈

Nullus 사용자가 자기 애플리케이션을 위한 파이프라인을 만들고 쿠버네티스에 배포하는 기능. internal/cicd/ + web/src/features/cicd/가 여기에 해당한다.

이 문서 분량의 대부분(1~12장)이 여기다.

② 저장소 자신의 CI/CD 파이프라인

Nullus 자체를 빌드·테스트·이미지 푸시·차트 배포하는 GitHub Actions 워크플로. .github/workflows/가 여기에 해당한다.

13장에서 다룬다.

Bounded Context로서의 CI/CD CLAUDE.md의 모듈 표에서 internal/cicd/는 CI/CD Pipeline 바운디드 컨텍스트이고, 핵심 Aggregate는 Pipeline과 Deployment다. 다른 모듈(stack, admin)의 internal 패키지를 직접 import하지 않는다는 규칙이 이 모듈에서 어떻게 지켜지는지는 3장 StackReader에서 확인한다.

2. 도메인 모델 — 무엇을 다루는가

internal/cicd/domain/pipeline.go. 이 파일에는 time 말고 어떤 import도 없다. 이게 Clean Architecture의 domain 레이어 규칙이다.

Pipeline — 배포 설정 Aggregate Root

type Pipeline struct {
    ID             string            // "pip_a1b2c3d4e5f6"
    Name           string
    ExecutionMode  string            // "ci" | "cd" | "ci_cd" | "stack_integrated" | "emergency_direct"
    TemplateID     string
    OrgID          string            // 조직 경계 — 목록 조회의 기준
    ClusterID      string            // 배포 대상 클러스터
    StackID        string            // 선택 — Stack 컨텍스트와의 연결고리
    Namespace      string
    AppType        AppType           // web | backend | batch
    GitRepoURL     string
    DockerfilePath string            // 비어 있지 않으면 "이미지 빌드가 필요한 파이프라인"
    DockerContext  string
    EnvVars        map[string]string // 설정 + 매니페스트 원문 + 레지스트리 자격증명이 모두 여기 들어간다
    Status         PipelineStatus    // active | inactive
    CreatedAt      time.Time
}
EnvVars가 하는 세 가지 일 — 이 모듈에서 가장 중요한 설계 관찰 EnvVars는 이름과 달리 단순한 "환경변수 맵"이 아니다. 실제로 세 가지 용도로 겸용된다.
  • 컨테이너 환경변수 — 생성된 Deployment의 env:로 주입
  • 매니페스트 원문 저장소 — NULLUS_MANIFEST_DEPLOYMENT / _SERVICE / _INGRESS 키에 사용자가 편집한 YAML 전문이 통째로 들어간다
  • 레지스트리 자격증명 — IMAGE_REGISTRY_URL, REGISTRY_USERNAME, REGISTRY_PASSWORD
전용 컬럼/테이블 대신 JSONB 맵 하나에 몰아넣은 구조라, 스키마 마이그레이션 없이 기능을 붙일 수 있는 대신 타입 안전성과 관심사 분리를 잃었다. 확장할 때 이 트레이드오프를 인지하고 손대야 한다.

Deployment — 실행 1회분 Aggregate Root

구조

  • ID — dep_ 접두사
  • PipelineID — 소속 파이프라인
  • Version — 프론트가 v0.1.{ms%1000}로 생성
  • Status — 아래 상태값
  • Steps []DeployStep — DB에 저장되지 않음. 조회 시점에 StepTracker(메모리)에서 채워 넣는다
  • StartedAt / CompletedAt / DeployedBy

상태값 5개 — 그중 실제로 쓰이는 건 3개

  • pending — 선언만 되어 있고 코드에서 대입되는 곳이 없다
  • running — Start()에서 즉시 설정
  • success — ApplyAsync() 정상 종료
  • failed — failDeployment()
  • rolled_back — 선언만 되어 있고 롤백 로직은 미구현 (14장 참고)

DeployStep — 진행률의 단위

type DeployStep struct {
    Name      string   // "Namespace 생성", "Docker Build" ...
    Status    string   // pending | running | success | failed
    Kind      string
    Message   string
    AppliedAt string
    Logs      []string // 이 스텝에서 출력된 로그 라인들
}

Deployment의 "진행 상태"는 DB가 아니라 메모리(StepTracker)에만 존재한다. API 서버가 재시작되면 진행 중이던 배포의 스텝 정보는 사라지고, DB의 status만 남는다. 또한 배포 종료 5분 뒤 time.AfterFunc로 트래커에서 제거된다. 이 수명주기를 6장에서 다시 본다.

PipelineTemplate / CICDGoldenPath

PipelineTemplate

재사용 가능한 파이프라인 골격. Stages []string(예: Build, Test, ImageBuild, Deploy)과 기본 EnvVars를 가진다. 파이프라인 생성 시 템플릿의 EnvVars가 먼저 깔리고 사용자 입력이 덮어쓴다.

CICDGoldenPath

검증된 도구 조합. Tools []CICDTool에 카테고리별 도구와 Helm/App 버전을 못 박아 둔다. 파이프라인 실행이 아니라 "무엇을 설치할지"의 카탈로그다. 11장 참고.

StackReader — 모듈 경계를 지키는 방법

CI/CD 파이프라인은 스택에 연결될 수 있다. 그러면 스택이 존재하는지, 같은 조직인지 검증해야 한다. 하지만 CI/CD 모듈이 Stack 모듈의 domain을 import하면 모듈 경계가 깨진다. 해결책은 CI/CD 쪽이 필요한 최소 정보만 담은 자기 소유 타입을 정의하는 것이다. 

// internal/cicd/port/stack_reader.go
type StackSummary struct {
    ID        string
    OrgID     string
    ClusterID string
    State     string // "completed", "failed", ...
}

type StackReader interface {
    // 스택이 없으면 (nil, nil) — 에러가 아니라 nil로 표현
    GetStackSummary(ctx context.Context, stackID string) (*StackSummary, error)
}

구현체 PostgresStackReader는 stacks 테이블을 직접 SELECT한다. DDD 용어로는 Anti-Corruption Layer이고, 헥사고날 아키텍처 용어로는 아웃바운드 포트다. 같은 원리가 반대 방향에도 적용된다 — PipelineHandler.RegisterStackRoutes()는 GET /api/v1/stacks/:stackId/pipelines를 CI/CD 핸들러가 직접 등록해서, Stack 모듈이 CI/CD를 import하지 않고도 해당 URL이 존재하게 만든다.

컴파일 타임 계약 검증 internal/cicd/port/interface_compliance_test.go는 테스트 함수가 하나도 없다. 대신 var _ port.PipelineRepository = (*cicdrepo.PostgresPipelineRepository)(nil) 같은 선언만 나열한다. 구현체가 인터페이스를 만족하지 않으면 테스트 실행 전에 컴파일이 깨진다. Go에서 흔히 쓰는 관용구다.

4-1. CreatePipeline — 검증 · 병합 · 모드 결정

4-2. ListPipelines — 단순하지만 분기 하나

StackID가 있으면 ListByStackID, 없으면 조직 기준 List. Postgres 구현은 양쪽 모두 ORDER BY created_at DESC LIMIT 100이다. 페이지네이션은 없고 상한만 걸려 있다.

4-3. DeployPipeline — 이 모듈의 심장

진입점이 세 개다. 이 세 개의 관계를 이해하는 것이 배포 로직 이해의 전부다.

Start(ctx, input)

검증 → 파이프라인 존재 확인 → Deployment 레코드를 running으로 생성하고 즉시 반환. HTTP는 여기까지만 기다린다.

ApplyAsync(deploymentID, ...)

고루틴에서 실행. 실제 이미지 빌드와 K8s apply를 수행하고 최종 상태를 DB에 기록. context.Background()를 새로 만들어 HTTP 요청 취소와 분리한다.

Execute(ctx, input)

Start + ApplyAsync를 동기로 이어붙인 뒤 DB를 다시 읽어 결과 반환. 주석에 명시된 대로 테스트와 하위호환용이다. 운영 핸들러는 쓰지 않는다.

BuildStepPlan — UI에 보여줄 단계 목록을 미리 계산

func BuildStepPlan(pipeline *domain.Pipeline, manifestTypes ...[]string) []string {
    steps := []string{"Namespace 생성", "Deployment 생성"}

    if pipeline != nil && pipeline.DockerfilePath != "" {
        hasRegistry := pipeline.EnvVars["IMAGE_REGISTRY_URL"] != ""
        imageStep := "Image Load"          // 레지스트리 없으면 kind load
        if hasRegistry { imageStep = "Image Push" }
        // 빌드 3단계를 앞에 붙인다
        steps = append([]string{"Git Clone", "Docker Build", imageStep}, steps...)
    }
    if includesOptionalManifest(selected, "service") { steps = append(steps, "Service 생성") }
    if includesOptionalManifest(selected, "ingress") { steps = append(steps, "Ingress 생성") }
    return steps
}
includesOptionalManifest의 "빈 목록 = 전부 포함" 규칙 manifestTypes가 비어 있으면 true를 반환한다. 즉 클라이언트가 아무것도 지정하지 않으면 Service와 Ingress가 모두 배포된다. 옵트아웃 방식이라는 점을 기억하라 — "빈 배열 = 아무것도 안 함"이라고 착각하기 쉽다.

5. 배포 전체 시퀀스 — 버튼 클릭에서 Pod까지

POST /api/v1/cicd/pipelines/:id/deploy 한 번의 요청이 만들어내는 전체 흐름이다. 핸들러(pipeline_handler.go:196)부터 순서대로 따라간다.

요청 바인딩 { version, deployed_by, manifest_types }를 받는다. 실패 시 400 PIPELINE_DEPLOY_INVALID.

[비동기] 이미지 준비 — 조건부 DockerfilePath != "" && imagePreparer != nil && clusterTargetProvider != nil일 때만 수행. 클러스터 타깃 조회 → 이미지 태그를 {파이프라인명}:{deploymentID 뒤 8자}로 생성 → git clone → docker build → (레지스트리 있으면 login+tag+push, 없으면 kind load docker-image) → stepOffset = 3 설정.

[비동기] 템플릿·포트 결정 AppType으로 매니페스트 템플릿 선택: web → react-spa, batch → python-fastapi, 그 외(backend 포함) → go-web-api. 포트는 imageRef가 있을 때만 명시(backend 8080 / batch 8000), 없으면 템플릿 기본값 사용.

임의의 YAML을 적용하려면 리소스 종류를 미리 알 수 없다. 그래서 typed client가 아니라 dynamic client + RESTMapper 조합을 쓴다.

클라이언트 2종 생성dynamic.NewForConfig(임의 리소스 조작) + discovery(API 서버가 뭘 아는지 질의).
RESTMapper 구성restmapper.NewDeferredDiscoveryRESTMapper(memory.NewMemCacheClient(...)) — GroupVersionKind를 실제 리소스 경로로 변환. 캐시 포함.
문서 분할utilyaml.NewYAMLReader로 --- 구분자를 처리. 매니페스트 하나에 여러 문서가 있어도 동작한다.

6-3. StepTracker — 진행 상태 저장소이자 pub/sub 허브

type StepTracker struct {
    mu          sync.RWMutex
    steps       map[string][]domain.DeployStep // deploymentID → 스텝들
    subscribers map[string][]chan LogEvent     // deploymentID → 구독 채널들
}

상태 변경 API

  • Init(id, names) — 전부 pending으로 초기화
  • MarkRunning / MarkSuccess / MarkFailed(id, idx, msg)
  • AppendLog(id, idx, line) — 스텝에 로그 한 줄 추가
  • Get(id) — 복사본 반환(외부에서 내부 슬라이스를 못 건드리게)
  • Remove(id) — 채널 close + 맵 삭제

동시성 처리 두 가지

  • 락 밖에서 publish — 상태 변경은 mu.Lock() 안에서, 이벤트 발행은 락을 푼 뒤에. 구독자가 느려도 락을 붙잡지 않는다.
  • 논블로킹 전송 — select { case ch <- event: default: }. 버퍼(64)가 차면 이벤트를 버린다. 느린 구독자 하나가 배포 전체를 멈추지 않도록 한 트레이드오프.

진행률은 단순히 (index+1) * 100 / len(steps)다. 마지막 스텝이 성공하면 이벤트에 Status: "success"가 실린다.

6-4. docker.Builder — 이미지 준비

os/exec로 CLI를 직접 호출한다(Docker SDK가 아니라). 각 명령 전에 실행할 커맨드 문자열을 AppendLog로 남겨서, UI에 $ docker build -t ...처럼 터미널 느낌으로 보이게 한다. 

tmpDir := os.MkdirTemp("nullus-build-*")   // defer os.RemoveAll

step 0: git clone --depth=1 {GitRepoURL} {tmpDir}
step 1: docker build -t {ImageName} -f {tmpDir/DockerfilePath} {tmpDir/DockerContext}
step 2: if RegistryURL != "" {
            docker login {URL} --username {u} --password-stdin   // 비밀번호는 stdin으로
            docker tag  {ImageName} {URL}/{ImageName}
            docker push {URL}/{ImageName}      → imageRef = 원격 참조
        } else {
            kind load docker-image {ImageName} --name {ClusterName}
                                               → imageRef = 로컬 태그
        }

각 단계는 실패 시 CombinedOutput() 결과를 로그로 남기고 MarkFailed 후 에러를 올린다. 스텝 인덱스가 0/1/2로 고정이라, 이 세 단계가 실행될 때 applyToCluster는 stepOffset = 3을 넘겨 매니페스트 적용을 인덱스 3부터 기록한다.

보안 관점 메모 비밀번호는 --password-stdin으로 전달해 프로세스 인자에 노출되지 않게 했다(좋은 습관). 다만 GitRepoURL과 경로들이 셸을 거치지 않고 exec.CommandContext 인자로 직접 들어가므로 셸 인젝션은 없지만, filepath.Join(tmpDir, opts.DockerfilePath)는 경로 탈출(../)을 검증하지 않는다. 신뢰 경계를 설계할 때 확인할 지점이다.

handler/errors.go의 errorResponse() 하나로 통일한다. 도메인 sentinel 에러를 HTTP 상태로 옮기는 매핑이 핸들러의 책임이다 — ErrStackNotFound → 400 STACK_NOT_FOUND, ErrStackOrgMismatch → 403 STACK_ORG_MISMATCH. DeletePipeline은 에러 메시지 문자열에 "not found"/"no rows"가 들어 있는지 검사해 404를 만드는데, 이건 sentinel 에러보다 약한 방식이다.

10. 리소스 조회 로직 — 배포한 것을 어떻게 다시 찾는가

GET /cicd/pipelines/:id/resources는 "이 파이프라인이 만든 쿠버네티스 오브젝트"를 찾아 돌려준다. 문제는 사용자가 직접 편집한 YAML로 배포되면 우리가 붙인 라벨이 없을 수 있다는 점이다. 그래서 3단계 폴백을 쓴다.

정확한 라벨 매칭nullus.io/pipeline-id={ID},app.kubernetes.io/managed-by=nullus-cicd
느슨한 라벨 매칭nullus.io/pipeline-id={ID}만으로 재시도
이름 기반 조회라벨로 못 찾으면 Get(ctx, pipeline.Name)으로 앱 이름과 같은 리소스를 직접 집는다

이 폴백을 Deployment / StatefulSet / Job / CronJob / Service / Ingress 각각에 적용한다. Pod은 한 단계 더 복잡해서, 라벨 → OwnerReference가 위에서 찾은 워크로드와 일치 → {앱이름}- 접두사 + managed-by 라벨, 순으로 매칭한다.

상태 판정 규칙

Kind판정 로직
DeploymentReadyReplicas == desired → running / UnavailableReplicas > 0 → degraded / UpdatedReplicas < desired → updating / 그 외 progressing
StatefulSetready==desired → running / CurrentReplicas==0 → pending / 그 외 progressing
JobFailed>0 → failed / Succeeded>0 → completed / Active>0 → running / 그 외 pending
CronJobSuspend → suspended / Active 있으면 running / 그 외 scheduled
PodWaiting/Terminated의 reason을 소문자로 그대로 노출(예: imagepullbackoff, crashloopbackoff) → 없으면 Running+모두 Ready면 running, 아니면 not_ready
IngressLoadBalancer 주소가 잡히면 running, 아니면 configured

Pod 상태를 자체 어휘로 번역하지 않고 쿠버네티스의 reason을 그대로 보여주는 선택이 눈에 띈다. 사용자가 그 문자열로 바로 검색할 수 있게 하려는 의도로 읽힌다.

접속 URL도 만들어 준다 — Ingress 규칙의 host, {svc}.{ns}.svc.cluster.local:{port}, ClusterIP 주소, NodePort면 <node-ip>:{nodePort}까지. 결과는 stage(ingress → service → workload → job → pod) → kind → name 순으로 안정 정렬한다.

PostgresClusterTargetProvider 어디서도 호출되지 않음 kind 클러스터명 조회 경로 미사용
PostgresStackReader NewCreatePipeline에 전달되지 않음 스택 존재·조직 일치 검증이 건너뛰어진다. ErrStackNotFound/ErrStackOrgMismatch는 발생하지 않음
StreamCicdLogs WebSocket 라우트 미등록 프론트 useCicdDeployLog도 미사용 → 실시간 스트리밍 없음, 2초 폴링으로 대체
useRollbackDeployment (프론트) 백엔드 라우트 없음 + URL 오류 axios baseURL이 /api/v1인데 경로에 /api/v1/...을 또 붙여 /api/v1/api/v1/...이 된다. 호출하는 컴포넌트도 없음
DeploymentStatusPending / RolledBack 어디서도 대입되지 않음 배포는 running → success/failed 세 상태만 오간다
Golden Path CRUD 메모리 저장소 변경 사항이 재시작 시 소실

파생 효과 — 스텝 라벨 어긋남

이 배선 상태가 만드는 구체적 증상 하나를 끝까지 따라가 보자.

위저드가 항상 dockerfilePath를 채워 보낸다dockerfilePath: dockerfileUrl || data.dockerfilePath
BuildStepPlan이 빌드 3단계를 앞에 붙인다스텝 목록이 [Git Clone, Docker Build, Image Load, Namespace 생성, Deployment 생성, ...]가 된다
트래커는 이 목록으로 초기화된다UI에는 빌드 단계가 표시된다
그러나 applyToCluster는 imagePreparer가 nil이라 빌드를 건너뛰고 stepOffset = 0으로 남는다ApplyWithTracking이 인덱스 0부터 기록을 시작한다
결과Namespace 적용 결과가 "Git Clone" 칸에, Deployment 적용 결과가 "Docker Build" 칸에 찍힌다. 라벨과 실제 작업이 어긋난다.
이 갭을 어떻게 읽을 것인가 위 항목들은 "버그 목록"이 아니라 구현 완료와 배선 완료가 다른 단계임을 보여주는 사례다. 빌드 파이프라인은 코드·테스트가 준비된 상태로 대기 중이고, main.go에서 WithImagePreparer(docker.NewBuilder(manifestApplier.Tracker))와 WithClusterTargetProvider(...)를 추가하면 활성화된다. Option 패턴을 쓴 덕분에 usecase 코드를 건드리지 않고 배선만으로 기능을 켤 수 있다 — 이게 DIP의 실용적 이득이다.

15. 이해도 점검

코드를 다시 열지 않고 답할 수 있는지 확인해 보라.

Q1. 배포 요청에 왜 200이 아니라 202를 돌려주는가? 그리고 ApplyAsync가 context.Background()를 새로 만드는 이유는?
답 보기

이미지 빌드·클러스터 적용은 장시간 작업이라 HTTP 요청을 붙잡으면 타임아웃과 중복 실행 위험이 있다. 그래서 작업을 등록만 하고(202 + deploymentId) 상태는 별도 조회로 분리했다. 요청 컨텍스트를 그대로 쓰면 클라이언트가 연결을 끊는 순간 배포가 취소되므로, 요청 생명주기와 분리된 새 컨텍스트를 만든다.

Q2. 사용자가 위저드에서 YAML을 편집했다. 그 YAML은 어디에 저장되고, 배포 시 어떻게 우선 적용되는가?
답 보기

pipelines.env_vars JSONB의 NULLUS_MANIFEST_DEPLOYMENT / _SERVICE / _INGRESS 키에 원문이 저장된다. applyToCluster의 firstNonEmptyManifest(envVars[key], generated.X)가 해당 키가 비어 있지 않으면 생성된 YAML 대신 저장된 원문을 쓴다. 컨테이너 env를 만들 때는 deployEnvVars()가 이 세 키를 제거한다.

Q3. CI/CD 모듈이 스택 정보를 검증해야 하는데, 왜 internal/stack/domain을 import하지 않는가? 대신 무엇을 쓰는가?
답 보기

모듈 간 직접 import는 바운디드 컨텍스트 경계를 깨뜨린다. 대신 CI/CD가 자기 소유 타입 port.StackSummary와 인터페이스 port.StackReader를 정의하고, 구현체 PostgresStackReader가 stacks 테이블을 읽는다(Anti-Corruption Layer). 반대 방향 필요는 RegisterStackRoutes로 CI/CD 핸들러가 /stacks/:id/pipelines를 직접 등록해 해결한다.

Q4. 배포가 끝난 지 10분 뒤 GET /cicd/deployments/:id를 호출하면 steps는 어떻게 되는가?
답 보기

비어 있다. 스텝 정보는 인메모리 StepTracker에만 있고, 배포 후 5분 뒤 time.AfterFunc이 Remove(depID)를 호출해 삭제한다. DB에는 status·시각·실행자만 남는다. 서버 재시작 시에도 마찬가지다.

Q5. manifest_types에 빈 배열을 보내면 Service와 Ingress는 배포되는가?
답 보기

배포된다. includesOptionalManifest는 목록이 비면 true를 반환하는 "빈 목록 = 전부 포함" 규칙이다. 제외하려면 원하는 것만 명시적으로 나열해야 한다(옵트아웃 방식).

Q6. 현재 배선에서 DockerfilePath를 설정한 파이프라인을 배포하면 컨테이너 이미지는 무엇이 되는가?
답 보기

imagePreparer가 주입되지 않아 빌드가 건너뛰어지고 imageRef가 빈 문자열로 남는다. 따라서 imageForContainer("", tpl.image)가 템플릿 기본 이미지를 반환한다 — backend/web이면 nginx:alpine, batch면 python:3.12-slim. 게다가 스텝 라벨은 빌드 3단계를 포함한 채 초기화되므로 진행 표시가 한 칸씩 밀린다(14장).
